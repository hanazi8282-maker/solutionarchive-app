# 케이스 승인 자동화 로드맵 — 단계·진입 조건·킬스위치

작성 2026-09-28 · 남헌 지시(09-28): 지금 켜지 않는다. 방향만 확정하고 준비한다.

- 스키마·연결 규칙의 정본: `reports/2026-09-28/case-approval-linkage-design.md`(이하 "연결 설계").
- 관련성 자동 승인(T2)의 정본: `reports/2026-09-28/approval-automation-design.md`(이하 "T2 설계"), 코드 `lib/analysis/auto-approval.ts`.
- 이 문서는 **"관련성 판정 자동화가 얼마나 검증되면 케이스 최종 승인까지 넓히나"** 의 수치를 정한다. 수치마다 근거 한 줄을 붙였다. 근거 없는 수치는 없다.

## 0. 원칙 셋 (기존 규칙과 같다)

1. **기계는 끄기만 한다. 올리는 것은 사람·역할 세션이다.** T2 설계 §3 "기계는 켜지 않는다", CLAUDE.md §10.2 표(무인 루프 ⛔). 단계는 리포 변수로 올리고, 무인 루프는 변수를 쓸 권한이 없다.
2. **한 단계의 성적은 그 단계 태그로만 센다.** `rr-v1`(관련성)·`ca-v1`(케이스)의 감사 창은 따로다. T2 설계 §6 — 새 조건의 오류가 옛 조건의 좋은 성적 뒤에 숨지 않게.
3. **확인 불가는 통과가 아니다.** 감사가 안 돌면 정확도 100% 가 아니라 "모른다" 이고, 모르면 끈다(CLAUDE.md §7.1, T2 설계 §3 "확인 불가도 끈다").

## 1. 단계 정의

| 단계 | 이름 | 기계가 쓰는 것 | 사람이 하는 것 | 변수 |
|---|---|---|---|---|
| 0 | 현재 | 없음 | 판정 채점 15/일 + 케이스 카드 10/일 | `AUTO_APPROVAL_ENABLED` 꺼짐 |
| 1 | 판정 행 자동 승인 | `review_relevance_verdicts.auto_approved_at` (`rr-v1`) | 감사 5/일 섞인 채점표 | `AUTO_APPROVAL_ENABLED=true` + `AUTO_APPROVAL_SINCE` |
| 2 | 케이스 후보 표시 | `case_moves.auto_candidate_at` 만 | `/cases/grade` 에서 후보 배지 보고 1클릭 승인/반려 | `CASE_AUTO_APPROVAL_STAGE=candidate` |
| 3 | 케이스 자동 승인 | `case_moves`·`case_studies` 의 `review_status`→`approved` + `auto_approved_at`·`auto_approval_rule='ca-v1'` | 감사 2카드/일 | `CASE_AUTO_APPROVAL_STAGE=approve` |

- 2단계는 **상태를 바꾸지 않는다.** 그래도 케이스 테이블 UPDATE 라 §10.1 밖이다 — 2단계 착수 전에 §10.1 개정(연결 설계 §7)이 필요하다.
- 3단계에서도 영구 사람 몫: 수치 있는 무브 · 부정 사례 · 연결 VOC 0건 무브 · 기존 케이스 60건(백필 불가) · 이식성 판정 · 등급 · 발행.

## 2. 단계 진입 조건 — 전부 수치

각 조건은 **주간 점검**(매주 월요일, 역할 세션 또는 사람)에서 잰다. 조건표를 `reports/<날짜>/case-approval-stage-<n>-entry.md` 에 실측값과 함께 남기고, 전부 충족일 때만 변수를 올린다. 한 조건이라도 "확인 불가" 면 미충족이다.

### 2-1. 0 → 1 (판정 행 자동 승인 가동)

T2 설계 §1 "켜는 법" 그대로. 수치만 다시 적는다.

| 조건 | 수치 | 근거 |
|---|---|---|
| 기준 통일 재시험 | 일치율 ≥ 90%, 표본 ≥ 100건(unknown 제외) | §10.1 조건 2. 09-28 실측 92.4%(85/92) 통과 — 단 Sonnet×Opus 였다 |
| **운영 조합 재확인** | Sonnet(1차)×Gemini(2차) 로 새 표본 ≥ 100건에서 ≥ 90% | `t2-criteria-retest.md` 한계 1 — 운영 2차는 Gemini 다. 판정자가 다르면 일치율은 다른 수다 |
| 마이그레이션 000027 적용 | 적용 + 확인 쿼리 양성·음성 통과 | 컬럼 없이는 승인을 기록할 자리가 없다 |
| 시행일 | `AUTO_APPROVAL_SINCE` = 기준 통일 PR 머지일(KST) | 옛 기준 1차 판정을 승인 입력에서 뺀다(`isFullAgreement`) |
| 감사 경로 | `relevance-grading-sample.mjs --audit 5` 가 채점표에 섞이는 것을 1회 드라이런으로 확인 | 조건 3 — 감사 없는 자동 승인은 성립하지 않는다 |

올리는 사람: 남헌 또는 역할 세션(CTO/CEO-STAFF). Notion 일일 상태 로그에 기록.

### 2-2. 1 → 2 (케이스 후보 표시)

"관련성 자동 승인이 믿을 만한가" 를 처음으로 수치로 묻는 문턱이다.

| 조건 | 수치 | 근거 |
|---|---|---|
| **감사 창이 찼다** | `rr-v1` 사람 채점(relevant/irrelevant) 누적 ≥ 100건, 최근 창 n = 50 | 킬스위치 창(`KILL.window=50`)이 한 번 완전히 교체된 뒤여야 "한 창의 운" 이 아니다. 5건/일이면 평일 4주 |
| **정확도** | 최근 50건 창 오류 ≤ 3건(47/50 = 94%)이 **4주 연속** 주간 점검 통과 | T2 설계 §6 "rr-v1 창 4주 연속 ≥93%(50건 중 오류 ≤3)" 와 같은 문턱(오류 건수 기준이 정본). p0=7% 기준선(소비재 1·2차 불일치 6.7%, 537건)의 절반이다 — 참 오류가 7% 면 이 검사는 절반쯤만 통과하고, 4% 이하면 대부분 통과한다(이항 계산). 그래서 "우연히 좋은 주" 로는 4주를 못 넘긴다 |
| **킬스위치 0회** | 최근 28일 `tripped`·`unverifiable` 0회 | 창 50건 ≈ 평일 2주. 그 2배 기간 동안 한 번도 안 꺼졌어야 "안정" 이다 |
| **SaaS 사람 정답** | SaaS 자동 승인 행의 사람 채점 ≥ 30건 포함 | 09-28 시점 SaaS 사람 채점 0건. 재시험 92.4% 는 "같게 읽는다" 이지 "맞게 읽는다" 가 아니다(`t2-criteria-retest.md` 한계 2). 30 = `KILL.minAudits`(10)의 3배 — 소비재 성적이 SaaS 를 대표하지 못하게 최소 표본을 따로 둔다 |
| **연결 재료가 있다** | `case_move_inputs` 마이그레이션 적용 + 연결 VOC ≥ 3건인 draft 무브 ≥ 20건 | 연결 설계 §2 P1. 표시할 후보가 없으면 2단계는 측정 불가다. 20 = 3단계 진입 표본(60)의 1/3 — 2단계 첫 달에 측정이 시작될 최소량 |
| **§10.1 개정** | 예외 2 문구가 CLAUDE.md 에 들어갔다 | 2단계의 `auto_candidate_at` UPDATE 부터 지금 §10.1 밖이다 |
| **CLI 승인 보정** | `case-review.mjs approve --move` 가 `reviewed_by` 를 쓴다 | 연결 설계 §8 — 판별자가 `reviewed_by IS NULL` 이다 |

### 2-3. 2 → 3 (케이스 자동 승인)

"사람이 후보를 실제로 승인했나" 를 잰다. 2단계에서 사람은 후보 배지를 보고 기존 버튼을 누른다. 후보였는데 사람이 반려한 것이 오류다.

| 조건 | 수치 | 근거 |
|---|---|---|
| **후보 정밀도** | 사람이 결정한 후보 무브 최근 60건 중 반려 ≤ 3건(≥ 95%)이 **4주 연속** | p0=5%. 관련성(7%)보다 엄격한 이유: 케이스 승인의 효과가 크다 — `/library` 공개·어드바이저 코퍼스·`cmo-daily` 앵글 선택이 전부 `approved` 를 읽는다. 60 = 카드 10/일 중 후보 2~3건/일 × 4~6주. 참 정밀도 95% 면 한 점검을 65% 확률로 통과, 85% 면 1.5% — 좋은 주가 4번 겹칠 수는 없다 |
| **반려 사유에 "VOC 무관" 0건** | 후보 반려의 `review_note` 를 사람이 분류해 "연결 리뷰가 무관했다" 가 0건 | 있으면 1단계 신호 자체가 틀린 것이다. 그 즉시 카운터를 0으로 되돌리고 1단계 감사를 다시 본다 |
| **누적 후보 결정 ≥ 100건** | 후보 무브 중 사람이 승인/반려한 것 누적 100 | 60건 창이 한 번 이상 완전히 갈린 뒤 |
| **1단계 안정 유지** | 최근 56일 `rr-v1` 킬스위치 0회 | 3단계는 1단계 위에 선다. 2단계 진입 조건(28일)의 2배 |
| **되돌리기 리허설** | §4 되돌리기 SQL 을 드라이런(count)으로 1회 돌려 대상 0건 확인 | §10.2 대량 UPDATE 4조건 중 "드라이런·롤백" |
| **감사 카드 경로** | `/cases/grade` 가 자동 승인 무브를 "검수" 로 다시 보여 주고 결정을 기록할 수 있다 | 3단계 킬스위치(§3)의 입력. 지금 `decideMove` 는 draft 에서만 결정한다(`app/cases/actions.ts:144`) — 자동 승인 행을 다시 결정하는 경로가 코드에 없다 |

### 2-4. 조건을 완화하는 확장(`ca-v2` 이후)

- 연결 최소 3건 → 2건, 수치 있는 무브 포함 등은 **새 태그**로 한다. 진입 조건은 "현재 태그 창 4주 연속 문턱 아래 + 되돌리기 리허설" 로 같다. 이 문서에 미리 수치를 적지 않는다 — 2·3단계 실측 없이 정한 수치는 근거가 없다.

## 3. 킬스위치 — 단계별

### 3-1. 1단계 `rr-v1` (구현됨, `killSwitch`)

- 창 50건 · p0 7% · 문턱 `ceil(n·p0 + 2√(n·p0(1−p0)))` = 8/50 · 워밍업 14일 · 최근 14일 감사 < 20건이면 확인 불가.
- 걸리면: 승인 0건, `agent_runs` blocked, Notion `사람판단필요=true`. 이미 찍힌 `auto_approved_at` 은 지우지 않는다(승인 효과가 "사람 줄에서 빠짐" 뿐이라).

### 3-2. 2단계 (후보 표시) — 킬스위치 없음, 대신 자동 내림

- 표시는 사람 결정을 바꾸지 않아 위험이 없다. 다만 **후보 정밀도가 최근 60건 중 반려 ≥ 7건**(`tripThreshold(60, 0.05)`=7, 정밀도 ≤ 88%)이면 배치가 배지를 멈추고 Notion 에 올린다 — 사람이 후보 규칙(`ca-v1` 조건 6개)을 다시 본다.
- 1단계 킬스위치가 걸리면 후보 표시도 같은 밤에 멈춘다(입력 신호가 죽었다).

### 3-3. 3단계 `ca-v1`

| 항목 | 수치 | 근거 |
|---|---|---|
| 감사 표본 | 자동 승인 무브 중 **2카드/일**을 `/cases/grade` 검수 줄에 섞는다 | 카드 10/일 예산(남헌 09-23 Q2-A) 중 20%. 케이스 카드는 판정 행보다 무거워 5/일은 못 한다 |
| 창 | 최근 감사 30건 | 2/일 × 평일 3주. 판정 행 창(50)보다 작은 이유는 표본 속도 |
| 오류 | 감사에서 사람이 반려(draft 로 되돌림)한 것 | 후보 정밀도와 같은 정의 |
| 문턱 | `tripThreshold(30, 0.05)` = **4건**(정확도 ≤ 86.7%) | 같은 산식, p0 5% |
| 워밍업 | 진입 후 14일, 감사 10건 전까지 오류율을 말하지 않는다 | `KILL.minAudits`·`warmupDays` 와 같다 |
| 확인 불가 | 워밍업 뒤 최근 14일 감사 < 8건이면 끈다 | 기대치 20건(평일 10일 × 2)의 40% — `minRecentAudits` 와 같은 비율 |
| 종속 | `rr-v1` 이 `tripped`/`unverifiable` 이면 `ca-v1` 도 같은 밤에 닫힌다 | 케이스 승인의 유일한 기계 신호가 관련성이다 |
| 눈가림 한계 | 감사 카드는 상태 배지를 숨기고 보여 준다. 그래도 자동 승인 행임을 완전히 숨길 수는 없다(승인 뒤 소비 경로에 이미 보인다) | T2 설계 위험 6 의 케이스 버전. 알려진 편향으로 기록한다 |

## 4. 되돌리기 — 걸렸을 때 이미 자동 승인된 케이스

### 4-1. 1단계가 걸렸을 때

- T2 설계 §5 그대로. 판정 행은 그대로 두고 새 승인만 멈춘다.
- 3단계가 켜져 있으면 **케이스 자동 승인도 멈춘다**(§3-3 종속). 되돌리지는 않는다 — 관련성이 의심스럽다는 것이지 케이스가 틀렸다는 증거는 아직 없다. 대신 최근 14일 `ca-v1` 승인 중 `reviewed_by IS NULL` 인 목록을 Notion 행에 붙여 사람이 우선 검수한다.

### 4-2. 3단계 `ca-v1` 이 걸렸을 때 — 기계가 스스로 되돌린다

§10.1 조건 4 의 문구가 이미 "스스로 끄고 `draft` 로 되돌아간다" 다. 케이스는 승인 효과가 실제(공개·코퍼스·앵글)라 되돌린다.

```sql
-- 대상: 기계가 승인했고 사람이 한 번도 안 본 무브. 드라이런은 count(*) 로.
UPDATE public.case_moves
   SET review_status = 'draft', auto_approved_at = NULL, auto_approval_rule = 'ca-v1:reverted'
 WHERE auto_approval_rule = 'ca-v1' AND reviewed_by IS NULL AND review_status = 'approved';
-- 케이스: 무브가 하나라도 draft 로 돌아간 자동 승인 케이스.
UPDATE public.case_studies s
   SET review_status = 'draft', auto_approved_at = NULL, auto_approval_rule = 'ca-v1:reverted'
 WHERE s.auto_approval_rule = 'ca-v1' AND s.reviewed_by IS NULL
   AND EXISTS (SELECT 1 FROM public.case_moves m WHERE m.case_study_id = s.id AND m.review_status = 'draft');
```

- 범위가 **자기 태그·사람 미개입** 으로 닫혀 있어 사람 승인은 절대 안 건드린다. `'ca-v1:reverted'` 를 남기는 이유는 되돌린 사실이 지워지지 않게(§7.1 — 행의 부재와 사건을 구분).
- 하류: 되돌린 무브를 `source_move` 로 가진 `content_items`·`posts` 는 그대로 둔다. `cmo-daily` 앵글 선택은 매일 `approved` 를 다시 읽으니 다음 날부터 안 뽑히고, 이미 스테이징된 `posts` 는 `pending_review` 라 사람이 발행 전에 본다(자동 발행 경로는 없다 — §10). 되돌린 무브 id 와 그 초안 목록을 Notion 행에 붙인다.
- `/library`·어드바이저 코퍼스 캐시(`CASE_CORPUS_TAG`)는 되돌리기 뒤 만료시킨다 — 배치가 못 하면 Notion 행에 "캐시 만료 필요" 를 적고 사람이 한다.
- 이 UPDATE 는 무인 루프가 하는 대량 UPDATE 다. **§10.1 예외 2 문구에 미리 적어 두는 것으로 허가한다**(연결 설계 §7 초안 3항). 적어 두지 않으면 §10.2 위반이다.

### 4-3. 다시 올리기

- 기계는 올리지 않는다. 걸린 원인을 사람이 적고(`reports/<날짜>/case-approval-kill-<n>.md`), 2-3 조건을 **처음부터** 다시 채운다(4주 연속 카운터 0 부터). 두 번 연속 걸리면 2단계까지 내리고 후보 규칙을 고친 새 태그(`ca-v2`)로만 다시 시도한다 — T2 설계 §6 "2회 연속이면 한 단계 더 내린다" 와 같다.
