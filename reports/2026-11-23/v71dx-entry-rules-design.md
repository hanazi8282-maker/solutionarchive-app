# v71dx 소스별 입구 규칙 설계 (꺼짐 기본, 초안)

- 코드: `lib/analysis/entry-rules.ts` (규칙 버전 `er-v1.1`)
- 연결: `lib/analysis/gradual-release.ts` `loadApprovalPool` 끝 — 기존 가드를 통과한 글을 한 번 더 거른다
- 셀프테스트: `scripts/entry-rules-selftest.mjs` · 리플레이: `scripts/entry-rules-replay.mjs`
- 켜는 스위치: `ENTRY_RULES_ENABLED=true` (없으면 아무 효과 없음) · `ENTRY_RULES_SHADOW=true` 면 판정만 기록하고 승인은 그대로

## 1. 왜 필요한가

사람 채점 60행(앱스토어 밖 6개 소스)을 보면 오류가 HN·포럼·github_issues 에 몰려 있다. 기존 가드 A/C/D 는 "양식 머리글·코드 토큰·설치 명령"처럼 확실한 표지만 잡는다. 그래서 6건은 정확히 잡았지만(정밀도 6/6), 표지가 없는 오류는 그대로 통과했다. 예를 들면 제품이 글에 안 나오는 HN 댓글, 자기 플러그인 홍보, 설치 순서 안내, API 진단 같은 글이다.

입구 규칙은 **"이 글이 제품 판단 재료인가"**를 유형 신호로 점수 매긴다. 승인 대상을 **좁히기만** 한다. 막힌 글은 버리지 않고 "사람 확인 대기"로 남는다.

## 2. 오류 유형 → 신호 → 규칙

| 오류 유형(남헌 규칙) | 보는 신호 | 규칙 |
|---|---|---|
| 개발자 대상(진단·코드·구조·API·플러그인 개발) | API·endpoint·OAuth·HTTP 4xx/5xx·JSON·schema·logic hook·webhook·PHP·apache·SMTP/DSN·REST·GitHub/커밋·patch/debug·callback·composer·migration·core 파일·frontend/backend 낱말(서로 다른 것 수), 코드 문법(``` · `{…;}` · `<Tag>` · `$var` · `->`) | 낱말 하나는 봐준다. 둘째부터 하나당 −8(최대 −48). 코드 문법은 −10 |
| 설치·운영 안내 | download from · install · set up · releases page/f-droid/.zip · click "…" · go to · then open/select/enter… · enter the · run the command · configure | 하나는 봐준다. 둘째부터 하나당 −10(최대 −40) |
| 자기 플러그인 홍보 + 설치 방법 | "I developed/built … plugin/add-on/tool" · "I'm the author" · disclosure / we build · my plugin · open to suggestions / check out my | 하나라도 있으면 −30 |
| 제품이 지나가며 언급됨(HN) | 머리 꼬리표를 뗀 본문에서 제품명이 몇 번 나오는지. "such as / like / e.g. / something like X"처럼 예시로 든 언급은 빼고 센다. 언급 앞뒤 250자 안에 이유·사실·사용자 목소리 신호가 있는지 | HN 은 제품을 "주어로, 판단과 함께" 말한 글만 통과. 언급이 0이면 −25 |
| 포럼 버그 신고(버전 머리글 + 고장) | 기존 가드 A/B 가 맡는다 | 입구 규칙은 따로 보지 않음(중복 안 함) |
| 개발자 설계 제안 | 개발자 낱말(schema·table)로만 간접 | **약함**. 이번 규칙의 놓친 오류 1건이 이 유형이다(§6) |
| github_issues | 소스 자체 | 언제나 막음 |

| 통과 유형 | 보는 신호 | 점수 |
|---|---|---|
| 사용 맥락이 있는 사용자 기능 요청 | 1인칭 사용(I use / we use / my team…) · 바람(I'd like / I want) · 요청 양식(Use case or problem / Proposed solution / please add…) · "users have to" | 사용자 목소리: 종류 하나당 +15(최대 2개) |
| 비교·가격·한계 사실 | because/so that · better than/vs/instead of · 가격(free·premium·$·per month) · 한계(doesn't allow · there is no · only works · not supported) · 동작 변화(changed·by default) · 평가어 | 이유·사실: 종류 하나당 +12(최대 3개) |
| 이유 있는 제품 평가 | 위 둘 + 제품 근처 | HN 은 제품 근처 신호가 있으면 +15 |
| 사용 맥락 | when/every time · on Android/desktop · workflow · daily/once a week | 종류 하나당 +7(최대 2개) |

## 3. 점수 정의

```
점수 = 30(출발점)
     + 사용자 목소리 15×min(종류,2)
     + 이유·사실   12×min(종류,3)
     + 사용 맥락    7×min(종류,2)
     + 제품 비중(HN 만): 판단과 함께 언급 +15 / 언급 없음 −25
     − 개발자 대상 8×(종류−1), 최대 48  − 코드 문법 10
     − 설치 절차  10×(종류−1), 최대 40
     − 자기 홍보 30
→ 0~100 으로 자른다. 점수 ≥ 소스 문턱이면 통과.
```

- **같은 신호가 여러 번 나와도 한 번만 센다**(종류 수). 긴 글이 낱말 반복으로 점수를 얻지 못하게 하려는 것이다.
- 개발자·설치는 **하나는 봐준다**. 사용자도 "API 가 없다", "설치했더니"처럼 한 번은 쓴다. 둘 이상 겹칠 때만 개발자·관리자 글로 본다.
- 머리 꼬리표 `[HN: 스레드 제목 …]`·`[YouTube 댓글 · …]` 는 수집기가 붙인 것이라 신호에서 뺀다. 스레드 제목에 제품명이 있어도 글쓴이가 말한 게 아니다.
- 흔한 영어 단어와 같은 제품명(rev·draft 등 짧은 목록)은 대문자로 쓴 것만 제품으로 센다. 글 id나 문장은 하나도 넣지 않았다.

## 4. 소스별 문턱과 근거

| 소스 | 문턱 | 왜 이 값인가(60행에 맞춘 값이 아닌 이유) |
|---|---|---|
| hackernews | 50 + "판단 근처 언급" 필수 | HN 은 여러 제품이 섞이는 일반 토론장이다. 이 제품을 실제로 말했는지가 1차 기준이다. 50 = 출발점 30 + 신호 두 개 정도로, "제품 근처 언급(+15)과 이유·평가 하나(+12)"면 넘는다. 숫자보다 **언급 필수 조건**이 결정적이다. 그 조건은 남헌 규칙 (3)(지나가는 언급 = 오류)을 그대로 옮긴 것이다. |
| suitecrm_community · mautic_forum · obsidian_forum | 35 | 포럼은 장소가 곧 제품이다. 그래서 제품명 신호를 쓰지 않는다. 35 = 출발점 + 아무 신호 하나에서 감점을 뺀 값이다. 남헌 규칙 "이유 없는 한 줄 증상 = weak(오류 아님)" 때문에 이유를 요구하지 않는다. **포럼 글은 감점(개발자·설치·홍보)으로만 막는다**는 뜻이다. |
| youtube | 30 | 댓글은 영상 아래 달리는 짧은 사용자 반응이다. 대명사("it")로 말하고, 발굴 프로젝트에는 제품명이 없다. 출발점 그대로 두어 감점이 있을 때만 막는다. |
| github_issues | 언제나 막음 | 남헌 결정. 기존 내용 가드도 이미 막는다. |
| 그 밖(appstore·googleplay·reddit 등) | 적용 안 함 | 이 규칙은 위 6개 소스용이다. 앱스토어·구글 플레이 사용자 후기는 손대지 않는다. |

가중치(15·12·7·−8·−10·−30)는 "신호 하나 = 문턱 차이 하나" 크기로 맞췄다. 홍보 −30은 다른 신호 두 개를 지운다. 자기 홍보 글은 이유를 길게 써도 홍보라는 판단(남헌 규칙 2)을 반영한 것이다.

### 조정 1회(이유)

1. **제품 비중을 HN 에만 적용.** 1차 손실 9건 중 대부분이 "제품명 없음 −25" 때문이었다. 포럼 답글은 장소가 제품이라 제품명을 쓰지 않는다. 이건 60행 결과가 아니라 소스 성격(단일 제품 포럼 vs 여러 제품 토론장)에서 나온 구분이다.
2. **포럼 문턱 35로.** "한 줄 증상은 weak, 오류 아님"(남헌 규칙)을 따랐다. 이유를 요구하면 그 규칙과 부딪친다. 포럼은 감점으로만 막는다.
3. **홍보 패턴 고침.** "I created my target list" 같은 일반 문장이 홍보로 잡혔다. "만든 것"이 플러그인·도구 명사일 때만 홍보로 본다. 패턴 결함 수정이다.
4. (2차 수치 뒤, 수치 변화 0) YouTube 를 제품 비중 대상에서 뺐다. 라벨 데이터에는 YouTube 제품명이 없어 영향이 없었다. 하지만 운영에서 competitor_url 로 제품명을 뽑으면 "it" 으로 말하는 좋은 댓글이 −25를 받는다. 리플레이 결과가 그대로인 것을 확인했다.

## 7. 한계·불확실한 점

- **표본 오염.** 규칙을 쓰기 전에 60행 원문을 읽었다. 낱말 목록은 유형 단위로 일반화했지만, 그 글들에서 본 표현이 목록에 들어간 것은 사실이다. 60행 수치는 학습 데이터 성적에 가깝다. 진짜 성적은 그림자 모드로 새 행에서 재야 한다.
- **HN 막힘 64%(무라벨 433행).** 정답이 없어 손실인지 모른다. 표본을 훑어보니 "My company uses Gusto for payroll"처럼 3인칭 회사 주어 사용 문장은 사용자 목소리로 안 잡혀 막힌 글이 있었다. 이번엔 고치지 않았다(조정 1회 제한). 그림자 모드로 막힌 HN 글 30건을 사람이 채점한 뒤 판단하길 권한다.
- **운영 제품명.** 리플레이는 라벨 파일의 프로젝트 이름을 썼다. 운영 연결부는 `analysis_projects.competitor_url` 호스트 첫 마디로 제품명을 만든다. 제품명 열이 따로 있는지 DB 를 보지 않아(이 작업은 DB 금지) 확인하지 못했다. 스토어·GitHub 주소면 제품명 없음으로 본다. 그때 HN 은 언급 필수 조건 없이 점수(50)만으로 판정한다.
- **영어 전용.** 신호 낱말이 영어다. 한국어 소스는 표에 없어 적용하지 않는다.
- **워크플로 배선 없음.** 승인 워크플로(`nightly-relevance.yml`·`relevance-approve-only.yml`)가 `ENTRY_RULES_*` 변수를 넘기지 않는다. 이번 작업은 워크플로를 고치지 않았다. 그래서 지금은 GitHub Actions 에서 켤 방법이 없다. 켜려면 두 파일 Auto-approve 스텝에 `ENTRY_RULES_ENABLED: ${{ vars.ENTRY_RULES_ENABLED || '' }}`·`ENTRY_RULES_SHADOW` 두 줄이 필요하다. build-check 에 셀프테스트를 등록하는 것도 같은 이유로 하지 않았다.
- **감사 창.** 입구 규칙은 대상 풀만 좁힌다. 킬스위치 감사 창(`loadGuardedAuditWindow`)은 건드리지 않았다. 감사 창이 느슨해지지 않는 쪽이다.
- **그림자 기록 위치.** 그림자 판정은 승인 로그 한 줄과 `agent_run_steps` approve 스텝 detail 의 `entry_rule` 집계(검사·막힘·소스별)로 남는다. 글별 판정을 DB 에 남기는 표는 만들지 않았다. 오케스트레이터가 `entryVerdict` 를 직접 import 해 DB 행에 돌리는 방식을 전제로 했다.
