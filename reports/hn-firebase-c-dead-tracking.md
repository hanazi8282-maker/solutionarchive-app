# HN Firebase 옵션 C — dead/deleted 지속측정

같은 표본(Airtable·Zapier, `search_by_date` page 0, 각 50댓글)을 날짜마다 다시 재서
아래에 **append** 한다. 덮어쓰지 않는다.

**왜:** Stage 2 실측(2026-09-10)에서 옵션 C 의 원래 목적 — Algolia 인덱스가 라이브
HN 보다 지연돼 남는 `dead`/`deleted` 댓글을 걸러내기 — 은 수집 시점 최근 댓글
50건 중 stale 0건으로 값이 안 나왔다. `docs/review-source-findings.md` 가설이
맞다면 **며칠 지나며** 그 댓글들 중 일부가 dead/deleted 로 바뀌어 stale 합이
커져야 한다. 그게 사실이면 C 가 필요하다는 근거가 되고, 계속 0 이면 A/B 로 충분하다.

- 측정 스크립트: `scripts/hn-firebase-c-track.mjs`
- 트리거: `.github/workflows/hn-firebase-c-probe.yml` — **2026-09-17 은퇴.** 09-15~09-17 은
  매일 자동 실행(`cron '23 15 * * *'`)이었고 지금은 `workflow_dispatch` 전용이다. 아래 §결론 참조.
- DB 미접속. 프로덕션 나이틀리 수집과 무관.

## 판독 기준

- **stale 합**(dead + deleted + 사라짐)이 날짜가 갈수록 커지면 → 인덱스 지연 가설이
  맞고, C 의 필터링 가치가 실재한다.
- 계속 0 근처면 → 최근 댓글에 한해 A/B 로 충분하다(C 요청비용 50배를 정당화 못 함).
- 3~5일(남헌 확인 후 조정) 쌓고 판단한다.

---

## 결론 (2026-09-17) — 위 판독 기준을 **적용하지 않는다**

**이 실험은 은퇴한다. 그러나 "stale 이 0 이라서 C 를 기각" 한 것이 아니다.
측정이 가설을 검증할 수 없는 설계였음이 드러나 검증 자체를 못 했다.**

### 왜 검증이 안 됐나

`scripts/hn-firebase-c-track.mjs` 는 매 실행마다 `search_by_date` + `page=0` 으로
**그 시점 최신 댓글 50건을 새로** 가져온다. 댓글 `objectID` 를 어디에도 저장하지 않는다
(168줄 전체에 코호트 persist 코드가 없다). 위 "같은 표본을 날짜마다 다시 잰다" 는
**쿼리 2개가 고정**이라는 뜻이었지 **댓글이 고정**이라는 뜻이 아니었다.

가설은 "수집한 **그 댓글들이** 며칠 지나며 dead/deleted 로 바뀌나" 인데, 측정은
"방금 올라온 댓글이 지금 dead 인가" 를 물었다. 갓 등록된 댓글은 당연히 stale 0 이다.
**0 이외의 값이 구조적으로 나올 수 없었다.** 5일을 쌓아도, 50일을 쌓아도 같은 0 이다.

데이터 자체가 이를 증명한다 — Airtable score max 가 `1242 → 1482 → 867`.
HN score 는 시간이 지나며 내려가지 않는다. **최대값이 떨어졌다는 것은 표본 집합이
바뀌었다는 뜻이다.** uniqueStories 도 27 → 36 → 33 으로 요동친다.

여기서 판독 기준("계속 0 근처면 → A/B 로 충분")을 그대로 적용하면
**측정 실패를 음성 결과로 확정**하게 된다. CLAUDE.md §7.1 "검사 방법이 주장과 같은지
확인하라" 위반이고, 이 리포의 여섯 번째 사례가 됐을 것이다.

### 그리고 질문 자체가 사라졌다

이 실험은 **"수집 단계에서 C 를 쓸까"** 를 묻고 있었다. 2026-09-17 남헌 결정으로
설계가 바뀌었다:

> **A 로 두루두루 넓게 모으고, 그중 많이 언급되고 강한 페인포인트로 보이는 것만
> C 로 실전성·효과성을 검증한다.**

C 는 수집 필터가 아니라 **인용 직전 검증 도구**가 됐다. 예산 계산도 이 쪽이 맞다 —
하루 200요청 상한에서 A 는 약 1만 댓글, C 를 수집에 쓰면 약 200건으로 **50분의 1** 이 된다.
반면 검증용으로는 상위 후보 10개 × 대표 댓글 3개 × (본인 1 + 대댓글 5) ≈ 180요청이면
충분하고, 매일 할 필요도 없다.

### 되살리려면

1. 1회차 댓글 `objectID` 50×2 를 JSON 으로 **고정 저장**
2. 이후 실행은 검색하지 말고 **저장된 ID 를 Firebase 로 재조회**

그 전까지 이 파일에 쌓이는 날짜는 판단 근거가 되지 않는다.
`workflow_dispatch` 는 남겨 뒀다.
