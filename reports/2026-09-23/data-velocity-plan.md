## TL;DR (3줄)

1. **수집이 아니라 "이해·검증(②)"이 멈춰 있다.** 리뷰 12,443건이 쌓였는데 속성 추출(extract)이 된 프로젝트는 1곳뿐, 15개 프로젝트는 추출 시도 0회, 속성 총 40개. extract 는 사람이 눌러야만 돌고(워크플로가 의도적으로 안 부름), 돌아도 프로젝트당 **가장 오래된 12만 자**만 읽는다. 리뷰를 더 모아도 이 층이 안 돌면 서비스 도출(③)로 못 간다.
2. **"타깃만 넣으면 하루 N건"은 성립하지 않는다.** HN `q:` 타깃 1개는 첫 실행에 400~700건을 받고 **그날로 exhausted** 로 닫힌다(자동 재활성화 없음). OKKY 는 글 1개 = 약 4건, 벨로그는 1건이고 글 목록을 긁는 코드가 없어 사람이 URL 을 대야 한다. 지금 타깃 90개 중 활성 3개(다나와 2·YouTube 1). SaaS 대량 유입 통로는 HN 하나이고, 그것도 "매일 새 타깃을 공급하는 구조"가 있어야 하루 단위가 된다.
3. **권고: 코드 0줄로 되는 것 4가지를 9/24 에 먼저 켜고(발굴 엔진 SaaS 타깃 상향·HN 질의 20개·초안 4건/일·transfer_note 필수 출력), 9/30 데모의 품질을 가르는 것은 "extract 야간 자동 실행 + 적합성 선별" 한 조각(≈8h)이다.** 이걸 넣으면 9/30 에 SaaS 속성 15~25개·승인 케이스 6건·실패 앵글 12~20행, 안 넣으면 SaaS 속성 0개인 채 리뷰만 1만 건 쌓인 화면이 된다.

## 2. ② 리뷰 이해·검증 — 목적 적합성 검수 전체 설계 (남헌 추가 요청)

**현재: 목적 적합성을 거르는 자리가 파이프라인 어디에도 없다.**
- 수집: 어댑터 `isRelevant()`(HN, 질의 토큰 부분문자열 포함 여부)와 `filtered`("남의 프로젝트 글")뿐. 러너는 텍스트 내용을 안 본다. 다나와·App Store 는 `filtered` 자체가 없다.
- 적재: `analysis_inputs` 1건=1행, 내용 판정 없음.
- extract: 입력을 전부 프롬프트에 밀어 넣고 **`created_at` 오름차순 12만 자**에서 뒤를 자른다(`lib/analysis/extract-run.ts:36, 242`). 무관 텍스트를 기각하지 않는다. 5,000건을 받아도 대부분 영영 안 읽힌다.
- remedy-gate: 리뷰가 아니라 **처방 카드**를 거른다. 무관 비율 실측 59.5% 가 이 층의 숫자다.
- 되먹임: `human_confirmed` 는 diff 로만 남고 다음 수집·추출에 반영되는 경로 없음. `saved_examples`(카카오)는 문체 학습 루프라 VOC 와 무관.
- SaaS 전제 충돌 4곳: extract 프롬프트 "이커머스 소구점 발굴"(문장 2개, 싸다) · **`remedy-judge.ts:53` "물리적 제품(실물 소비재)를 파는 셀러"(SaaS 처방을 스스로 무관 처리)** · `pain-terms.json` 41낱말 소비재 · `productKindOf()` 2갈래.

**제안: 4층 게이트. 원칙 = 싼 층에서 먼저 거르고, 확인 불가는 어느 쪽으로도 접지 않는다(§7.1), LLM 은 플래그만 하고 승인·반려는 못 쓴다(§10.1).**
- **T0 타깃 설계 = 첫 번째 필터, 비용 0.** 질의가 곧 적합성이다. HN `q:` 는 브랜드명이 아니라 **문제 유형별 페인 구절**로 짠다 — `config/reader-problems.json` 7유형(MAKE_BUT_NO_MONEY·NO_FIRST_CUSTOMER·PRICE_TOO_LOW·ONE_OFF_ONLY·NO_CHANNEL·SOLO_CEILING·NOBODY_TRUSTS_ME)당 2~3개, 예: `q:churn saas`, `q:pricing page conversion`, `q:first paying customer`, `q:cold email founder`, `q:solo founder burnout`, `q:cancel subscription why`. 20개 = 2h(사람). 단 HN `isRelevant` 가 토큰 전부 포함을 요구하므로 3토큰 이하로.
- **T1 규칙 프리필터(extract 입력 선별), 코드 ≈3h.** 오래된 순 12만 자 대신 **SaaS 페인 낱말 사전(pain-terms SaaS판 재사용) 히트 수 × 길이 × 최신성**으로 상위 12만 자를 고른다. 버린 건수를 `droppedInputs` 로 반환·로그에 남긴다(0건 추출과 "다 버렸다"를 가른다). LLM 0원.
- **T2 LLM 관련성 판정, 표본에만.** `remedy-judge.ts` 복제, 3상태 **관련/무관/확인불가**(mock·파싱 실패·라벨 누락 = null). T1 통과분 중 프로젝트당 상위 N(예 200건)만 판정, 야간 배치. 결과는 `analysis_inputs` 에 컬럼이 아니라 별도 판정 캐시(remedy_verdicts 와 같은 모양)에. 사람 판정(`human_verdict`)이 항상 이긴다. 비용 Gemini ≈$0.001/프로젝트 실측 기준 × 표본 배수.
- **T3 사람 카드 채점, 하루 10장.** 두 자리: (a) 속성 단위 `human_confirmed`(이미 `/analyze/[id]/review` 에 있음) (b) T2 판정 표본 10장 관련/무관 채점 → 정밀도 측정(21장 채점표 선례, import 스크립트는 아직 없음 → 만들어야 한다). 이 채점이 T2 프롬프트의 few-shot 으로 되먹임되는 경로를 신설(간단히: 최근 사람 판정 N건을 프롬프트에 주입).
- **T4 remedy-gate(기존)** — 카드 단계는 그대로. 단 `remedy-judge.ts:53` 문장을 질의 종류(physical/saas)로 갈라 준다(1줄).
- 검수 화면: 리뷰 단위 관련/무관 화면은 **새로 만들지 않는다**. T3(b) 는 마크다운 채점표 + import 로 간다(선례 재사용). 속성 검수 화면은 이미 있다.

**③ 서비스 도출에 대한 한 줄 진단(cto):** `O = I + max(I−S, 0)` 의 `S` 는 공급·경쟁 충족도가 아니라 **같은 텍스트에서 LLM 이 매긴 불만 톤**이다. SaaS 댓글에서 "가장 크게 불평하는 지점"은 짚지만 "아무도 안 만드는 지점"은 못 말한다. MVP 는 전자로 간다(페인 → reader_problem → 케이스 매칭). 공급측 관측(경쟁 도구 언급·failed_angles)은 10/4 이후.

## 4. B. 케이스 조사 속도

**B(1) 승인 병목 — 실태**
- 한 케이스 승인 = 무브 2개 × (근거 펼치기 1 + 이식성 라디오 1 + 승인 1) + 케이스 근거 1 + 케이스 승인 1 ≈ **8클릭·폼 제출 3회**. 케이스와 무브 **둘 다** approved 여야 매칭에 들어간다.
- 승인 기준 문서는 **없다**(`evidence-rules.md` 는 등급 산식만, 승인 판정표 0, `case-readability-guide*` 파일 없음). 코드 경고 2개와 사람 머릿속.

## 5. C. 자동 확장 로직 — 발굴 엔진 재활용 (권고 (a))

**현재 엔진**: `nextKind()` 가 physical/saas 를 격일로 → `claude -p` 후보 2건 → 사전 게이트(중복·포화 3) → 프로브(saas = HN `nbHits`) → 창 30≤hits≤500 이면 `analysis_projects(collecting)` + `review_targets(active)` 자동 등록 → 야간 수집 → **extract 는 사람 클릭** → `/discovery` 사람 검증(killed 는 타깃까지 닫음). 크론 KST 02:13, `DISCOVERY_TARGET` 2/일, `timeout 20분`.
- **DB 실측: SaaS 후보 6건(Notion 79,077 · Slack 73,041 · Stripe 38,548 · 1Password 12,129 · Figma 10,555 · Datadog 3,576) 전부 `oversized_voc > 500` 으로 자동 기각.** physical 은 채택 5·기각 1. 즉 SaaS 축은 켜져 있으되 **한 건도 통과한 적이 없다.**
- 원인은 창이 아니라 **제안 프롬프트**다: "HN 에서 그대로 검색할 영문 제품명"을 요구하니 LLM 이 대형 브랜드만 낸다. 창 30~500 은 오히려 1인 창업가 이식성에 맞는 규모(cto 판단, 나도 동의).

**3안**
- (a) **최소안 — 코드 0~1줄.** ① `vars.DISCOVERY_TARGET` 2→4, `DISCOVERY_KIND=saas` 고정(9/30 까지) ② 제안 프롬프트에 "1인·소규모 팀이 만든 인디 SaaS, HN 언급 수백 건 규모" 조건 한 줄 ③ 채택 후보에 **페인 구절 타깃**(§2-T0)을 짝으로 붙이는 건 사람이. ≈1h + 프롬프트 1줄. 첫 결과 그날 밤 02:13. 되돌릴 수 있다.
- (b) 시드를 `bottleneck × reader_problem` 조합에서 자동 생성 — 6~10h. 기각 사유: 프로브가 **이름** hits 로 재는데 시드는 **카테고리 구문**이라 대부분 `insufficient_voc`. 프로브 재설계가 선행 → 최소안이 아니다. 10/4 이후 재검토.
- (c) 신설 20h+ — 기각. robots 캐시·판정·적재·검증 화면 전부 버린다.
- **권고 (a).** 단 (a) 만으로는 "브랜드 → 댓글" 축이고 "페인 구절 → 댓글" 축은 T0 사람 등록이다. 둘을 같이 돌려 어느 쪽 적합성이 높은지 T3 채점으로 1주 안에 비교한다.
