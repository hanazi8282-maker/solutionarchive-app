# 평가 세트 (Eval Set) — 정답이 알려진 30문항

> **성격**: 두 아카이브의 **실측 대조 사례**로 만든 문제집. 정답과 해설이 원문에 이미 있다.
> **위치**: `methodology/content/eval-set.md`
> **참조**: `solfa/01-methodology.md` / `pdp/01-methodology.md` / `00-gate.md` / `cross-decisions.md`

---

## 0. 이 파일이 존재하는 이유

게이트를 만들어도 **내 판정이 맞는지 알 수 없다.** D+30을 기다려야 하기 때문이다.

그런데 두 원문에는 **정답이 이미 알려진 대조 사례**가 수십 건 있다. 같은 조건에서 한쪽은 터지고 한쪽은 안 터졌고, **왜 그런지까지 원문이 분석해두었다.**

```
문항: [A안] vs [B안] — 결과를 가림
정답: 어느 쪽이 더 나왔는가 + 왜인가 (원문 분석이 정답지)
```

### 용도 3가지

| 용도 | 방법 |
|---|---|
| **① 내 판정 능력 측정** | 30문항을 풀고 정답률을 낸다. 오늘 당장 가능 |
| **② 스킬 품질 측정** | `solfa-gate` / `pdp-gate` 스킬에 문항을 던져 점수를 낸다. 스킬을 고쳤을 때 좋아졌는지 나빠졌는지를 감이 아니라 점수로 안다 |
| **③ 규칙 신뢰도 역산** | 특정 규칙(R-xx / P-xx / C-xx)이 걸린 문항에서 반복적으로 틀리면 **그 규칙을 내가 잘못 이해하고 있는 것** |

### 채점 방식

각 문항은 **2점**이다.
- **선택 1점** — 어느 쪽이 더 나왔는가
- **근거 1점** — 원문이 제시한 이유와 **같은 규칙**을 지목했는가 (표현이 달라도 규칙이 같으면 정답)

**만점 60점.**

| 점수 | 해석 |
|---|---|
| 54점 이상 (90%) | 두 방법론이 내면화됨. 게이트 없이도 판정 가능 |
| 42~53점 (70~89%) | 실전 투입 가능. 틀린 문항의 규칙을 재학습 |
| 30~41점 (50~69%) | 게이트를 반드시 돌려야 하는 단계 |
| 30점 미만 | 역방향(G-R) 세션을 먼저 20건 돌린다 |

> ⚠️ **선택은 맞았는데 근거가 틀린 경우가 가장 위험하다.** 우연히 맞힌 것이므로 재현되지 않는다.

## 1. 사용법

1. **정답을 가리고** 문항만 읽는다 (§3은 접어두거나 별도 파일로 분리)
2. 각 문항에 **선택 + 근거(규칙명)**를 적는다
3. §3에서 채점한다
4. 틀린 문항의 **규칙 코드**를 모은다 → 그 규칙이 내 약점이다
5. 해당 아카이브의 `solfa/04-decisions.md` 또는 `pdp/04-decisions.md`에 약점 규칙을 기록하고, 다음 초안에서 그 규칙을 의식적으로 적용한다

**Claude에게 시킬 때**: 문항만 주고 답을 받은 뒤 §3으로 채점한다. 스킬 수정 전후 점수를 비교한다.

## 5. 확장 방법

이 세트는 **30문항이 끝이 아니다.**

### 5-1. 역방향 세션에서 문항을 추가한다
G-R로 분석한 남의 콘텐츠 중 **"내 게이트로 탈락시켰겠는데 실제로는 터진 것"**은 그대로 문항이 된다. 정답은 실측 조회수다.

```markdown
### Q31. [외부관찰 LOG-YYYYMMDD-nn]
[카피 A] vs [카피 B] — 어느 쪽이 더 나왔나?
정답: (실측) / 근거: (역방향 분석 결과)
```

### 5-2. 세 번째 자료가 들어오면
새 SEED와 기존 SEED가 갈리는 지점이 **교차 문항**이 된다. Q28~Q30이 그 형식이다.

### 5-3. 스킬 평가로 전환
`skill-creator`의 eval 형식으로 변환하면 자동 채점이 가능하다.
- 입력: 문항 텍스트
- 기대 출력: 선택 + 규칙 코드
- 채점: 규칙 코드 일치 여부

**스킬을 수정할 때마다 이 30문항을 돌려 점수를 비교한다.** 좋아졌는지 나빠졌는지를 감이 아니라 점수로 안다.

## 6. 재실행

§5-3 이 말한 "스킬을 수정할 때마다 돌린다"를 실제로 돌리는 절차다.
하니스는 `scripts/run-eval.mjs` 다 (설계는 `_setup/prompt-B-CC.md`).

### 6-1. 언제 돌리나

- `.claude/skills/content-gate/SKILL.md` 를 고쳤을 때
- `references/` 를 갱신했을 때 (`scripts/sync-content-skill.sh`)
- 규칙 SEED(`<자료>/04-decisions.md` §2)나 `cross-decisions.md` 를 갱신했을 때

### 6-2. 명령어

```bash
node scripts/run-eval.mjs --runs 3          # 표준. 결과는 eval/results/ 에 쌓인다
node scripts/run-eval.mjs --runs 1 --only 1,2,3   # 파일럿
node scripts/run-eval.mjs --mock-perfect --runs 1 # 채점기 자체 점검 (모델 호출 없음)

# 채점기만 고쳤을 때 — 저장된 응답 원문을 다시 채점한다. 모델을 부르지 않는다
node scripts/run-eval.mjs --regrade methodology/content/eval/results/raw/<날짜>-<해시>.json
```

**모델 호출과 채점은 분리돼 있다.** 실행할 때마다 응답 원문이
`eval/results/raw/` 에 JSON 으로 남고, `--regrade` 가 그걸 다시 읽는다.
채점 기준을 손볼 때 90번을 다시 호출하면 비용도 문제지만 **응답이 실행마다
흔들려서 채점기 변경의 효과를 분리할 수 없다.** 원문을 고정한 채 채점만
바꿔야 "채점기가 좋아졌다"를 말할 수 있다.

**채점기를 고쳤으면 양 끝을 다시 확인해라.** 한쪽만 보면 속는다.

```bash
node scripts/run-eval.mjs --mock --runs 1 --no-write          # 쓰레기 응답 → 10/60 근처여야
node scripts/run-eval.mjs --mock-perfect --runs 1 --no-write  # 정답 그대로  → 60/60 이어야
```

앞이 높으면 채점기가 헐거워진 것이고, 뒤가 낮으면 맞는 답도 틀렸다고 하는
것이다. 둘 중 하나라도 어긋난 상태의 점수는 스킬 실력이 아니라 채점기 버그다.

**1회 실행 결과를 그대로 믿지 마라.** LLM 응답은 실행마다 흔들린다. 3회를 돌려
`안정 정답 / 불안정 / 안정 오답` 으로 갈라야 진짜 약점이 보인다. 3회 중 1~2회만
맞은 문항이 우연에 가장 가깝다.

### 6-3. 판정

- **이전 베이스라인 대비 -4점 이상이면 회귀다. 수정을 되돌린다.**
- ⚠️ 문항이 추가되면 만점이 바뀐다. 점수가 아니라 **비율(%)로 비교**한다.
- ★ **선택 O · 근거 X** 건수를 먼저 본다. 이게 많으면 총점이 높아도 신뢰하면 안 된다.
  규칙을 적용한 게 아니라 찍어서 맞힌 것이라 다음 판정에서 재현되지 않는다.
- ⚠️ **C-01 에서 2개 이상 틀렸으면 최상위 경고.** 두 방법론이 완전히 일치한
  유일한 영역이라 여기서 틀리면 나머지 점수가 무의미하다.
- 리포트의 `스킬 로드 확인` 이 실행 수보다 적으면 그만큼은 스킬 점수가 아니라
  모델 기본 점수다. 점수를 스킬의 공으로 돌리기 전에 이 줄을 봐라.
- `수동확인` 으로 마킹된 서술형은 **오답이 아니라 채점 불가**다. 사람이 직접 본다.
  0점으로 접으면 "틀렸다"와 "채점 못 했다"가 섞인다 (CLAUDE.md §7.1).

### 6-4. 하지 말 것

- ⚠️ **점수가 낮다고 스킬을 고치지 마라.** 하니스는 측정만 한다. 수정 여부는
  결과를 보고 사람이 결정한다. 점수에 맞춰 스킬을 깎으면 그 점수는 더 이상
  아무것도 측정하지 않는다.
- **문항을 고치지 마라.** 정답이 두 원문의 실측에 묶여 있다.
- ⛔ `eval/answers.md` 를 스킬 `references/` 나 프로젝트 지식, 프롬프트에 넣지 마라.
