## 0. 먼저 — 확인 못 한 것과 전제

- (확인 불가) `review_sources.daily_request_cap`·`min_interval_ms` 의 **DB 실값**. 아래 cap 은 마이그 시드 기준(000024 3배 인상 반영). 야간 `review-request-cap.mjs` 가 2배 이내로 올릴 수 있어 실값은 더 클 수 있다.
- (정정) clien 간격은 한도표의 3000ms 가 아니라 **5000ms** 다 — 시드 마이그 `20260919000001` 이 robots Crawl-delay 5 를 지키는 유일한 장치로 5000 을 넣었고 뒤에 바꾼 마이그가 없다. 아래 계산은 5000 을 쓴다(한도표의 clien 23.1분은 38.5분으로 읽어야 한다).
- (코드 사실) 하루 요청 수는 `review_collection_runs.requests` 를 **UTC 날짜**로 합산한다(`store.ts loadSource`). 슬롯은 cron 2개(05:37Z·17:37Z, `nightly-review-collect.yml`)라 한 UTC 날 = 슬롯 2개. '하루' 판정도 이 UTC 날을 쓴다 — 다른 날짜를 쓰면 cap 집계와 어긋난다.
- (코드 사실) 차단 신호 측정 칸은 `review_collection_runs.blocked_responses`(403·429·WAF·엄격모드 빈응답·캡차) 와 `quota_responses`(공식 API 쿼터 소진, 차단 아님)다. 마이그 000033 은 09-28 적용 기록 있음(`docs/migration-exceptions.md`). 그 전 행의 0 은 '측정 안 함'이다.
- (코드 사실) 램프 엔진은 main 에 없다. `lib/review/ramp.ts` 는 타깃 수 계단 `[10,15,22,30]` 읽기 + 브랜치 `feat/ramp-wiring` 의 차단 시 되돌리기(`rollbackOnBlock`, 동결 3일)뿐. 올리는 코드는 어디에도 없다. 이 문서의 '퍼센트 단계'는 **타깃 수 계단과 다른 손잡이**(하루 요청 수)다 — §6 에서 둘의 관계를 정한다.
- (실측 인용) 66회 실행 신규 1,442건 중 hackernews 1,071건(74%). 타깃을 방문한 소스는 7개(hackernews·bobaedream·okky·clien·disquiet·velog·indiehackers), 켜진 소스 중 **11곳은 타깃 0개 방문**(오케스트레이터 실측 — v22 §1-2 의 15개는 분모가 달랐다).
- 시간 한도 = 2슬롯 × 90분(`timeout-minutes: 90`) = **180분**. 소스는 직렬이다. 아래 '실행 시간'은 요청 수 × 간격의 **하한**이다(응답 지연·DB 쓰기 제외 — 09-28 실측은 이론값보다 훨씬 길었다, §7).

## 3. 하루 총 실행 시간 — 단계별 합계와 180분 초과 시 배분

- 상한 100% 합(18소스, 요청×간격): 400+1,200+900+1,107+900+1,008+300+750+**2,310**+900+1,200+1,200+**4,320**+250+360+240+240+320 = **17,905초 = 298.4분**. youtube(a→c) 4,320 과 clien 5000ms 정정이 한도표(216.3분)와의 차이다.
- 단계별(배분 전): 50% 149.2분 · 60% 179.1분 · 70% 208.9분 · 80% 238.7분 · 90% 268.6분 → **70% 부터 180분 초과**.
- youtube 를 cap 200 으로 묶어도(합 13,785초 = 229.8분): 50% 114.9 · 60% 137.9 · 70% 160.8 · 80% 183.8 · 90% 206.8 → 80% 부터 초과. 즉 youtube 와 무관하게 정적 합은 180분을 넘는다.
- 배분 규칙 A(정적, 균등 시간 몫 water-fill): 180분을 18소스에 10분씩 나누고, 상한×간격이 몫보다 작은 소스는 제값, 남는 시간을 나머지에 다시 균등. 결과: 제값 유지 8곳(appstore 400s·tumblbug 300·brunch 750·disquiet 250·devto 360·yozm 240·indiehackers 240·googleplay 320), 나머지 10곳은 각 **794초**. 요청 수로 hackernews 397 · damoang 264 · 82cook 264 · theqoo 264 · bobaedream 264 · clien 158 · fmkorea 264 · okky 198 · velog 198 · youtube 794. 합 10,800초 = 정확히 180분. 단계별 90 / 108 / 126 / 144 / **162분**.
- A 의 대가: hackernews 상한이 600→397, 90% 목표 357 — **지금 가장 생산적인 소스가 지금보다 못 돈다**. 타깃 0 인 11소스가 쓰지도 않을 시간을 쥐고 있어서다.
- 배분 규칙 B(동적, 권고): 배분 분모를 **active 타깃이 있는 소스만**으로 한다. 매일 pre-step 이 `review_targets` active 수를 읽는다(`review-request-cap.mjs` 가 이미 같은 값을 읽는다 — 새 조회 없음). 오늘 분모 7소스 합 = 1,200+1,008+1,200+2,310+250+1,200+240 = 7,408초 = **123.5분** < 180 → 배분 발동 없음. 단계별 61.7 / 74.1 / 86.4 / 98.8 / **111.1분**. 타깃이 생긴 소스가 분모에 들어오는 날 합이 180 을 넘으면 그날부터 A 의 water-fill 을 그 분모 안에서 돌린다.
- B 의 대가: 소스별 상한이 날마다 바뀔 수 있어 '단계 %'는 그대로여도 목표 요청 수가 흔들린다 → 요약 줄에 상한을 같이 찍는다(§6). 배분이 걸린 날은 그 소스의 '정상'을 (5)의 공급 부족과 같은 보류로 본다(목표 자체가 줄었으니 실측이 아니다).
- 규칙 C(비례 축소 10,800/17,905 = 0.603 배): 작은 소스(yozm 40→24)도 같이 깎여 공급 많은 곳이 유리. 권고하지 않는다.
- 어느 규칙이든 결과 합 ≤ 180분 × 90% = 162분이 **이론 하한**이다. 09-28 실측(소스 1건 130~489초, 이론 26초)대로면 실제는 이보다 길어 타임아웃이 먼저 온다 — §7 위험 1.

## 4. hackernews 74% 편중이 이 규칙으로 풀리는가

- 편중 가드 40% 의 기준은 **요청 수(=실행 시간)** 로 정한다. 근거: 우리가 조절하는 손잡이도, 호스트가 막는 기준도 요청이다. 수집 건수는 수율(hackernews 35.7건/타깃 vs clien 4.5건/타깃)의 결과라 조절 대상이 아니다.
- 요청 기준으로 hackernews 는 이미 가드 안이다: 상한 600 × 2s = 1,200초 = 180분의 **11.1%**. 실측 요청 몫은 오케스트레이터가 주지 않아 확인 불가이나, 회당 13요청이면 하루 26요청 — 가드 근처도 아니다.
- 따라서 **이 규칙은 74% 를 직접 풀지 않는다.** 수집 건수 기준으로 가드를 걸면 hackernews 요청을 깎아야 하는데 그러면 총량만 준다(다른 소스는 타깃이 없어 늘지 않는다). 74% 의 원인은 편중이 아니라 11소스 타깃 0 이다.
- 규칙이 기여하는 부분: 타깃이 공급되면(v22 §1-6, 제품 사전 투입) bobaedream·okky 등이 50%→90% 로 오르며 분모가 커진다. 그때 B 배분이 hackernews 를 깎지 않고도 합을 180분 안에 둔다. 공급 없이 단계만 올리면 hackernews 몫만 커져 74% 는 오히려 오른다 — 그래서 (5)의 '공급 부족 = 보류'가 필요하다.

## 5. 타깃이 없어 목표를 못 채우는 소스 — 정상 판정 규칙

- '정상 완료' 정의(하루, UTC): 그 소스의 그날 `review_collection_runs` 행 전부가 `blocked_responses=0 ∧ quota_responses=0 ∧ status='ok'`(failed·interrupted 없음) ∧ `health_after` 에 broken 없음. 요청 수는 보지 않는다 — 차단·오류 없음 = 정상.
- '공급 부족' 표시: 정상 ∧ 그날 실제 요청 < **직전 단계 목표**(= 이번 목표 − 상한×10%p; 50% 단계면 40%). 근거 있는 선택: 단계 간격이 10%p 라 그보다 덜 쓴 날은 이번 단계를 시험한 날이 아니다(기껏해야 전 단계). 하루 요청 0(타깃 0 방문)도 여기 들어간다.
- 대안 A(공급 부족일도 정상 1일로 센다): 타깃 0 소스가 이틀마다 한 단계씩 올라 8일 뒤 90% '안정 소스'가 된다 — 한 번도 그 양을 보내 본 적 없이. 타깃이 들어오는 날 90% 로 첫 실측을 하고 차단되면 그때 하강한다. 램프가 보호하는 게 없다.
- 대안 B(권고 — 보류): 공급 부족일은 연속 정상 일수에 **넣지도 리셋하지도 않는다**(유지). 단계는 실제로 그 양을 보낸 날 2일 연속에만 오른다. 대가: 타깃 공급이 늦으면 소스가 50% 에 오래 머문다 — 그러나 50% 목표조차 못 채우는 소스라 머무는 데 비용이 없다.
- 하루 2슬롯 중 하나만 돈 날(워크플로 미발화·타임아웃으로 뒤 소스 미실행): 행이 없으면 '측정 없음'으로 공급 부족과 같은 보류. interrupted 는 오류라 정상이 아니다(리셋은 아님 — 리셋은 차단 신호만).
- 요약 줄에 `공급` 칸을 둔다: `충족` / `부족(요청 n/목표 m)` / `측정 없음`.

## 6. 스키마·PR 분해 (설계만, 마이그 미작성)

- `review_source_ramp` 현재 칸: `source_key`(PK, FK) · `level smallint CHECK 0~3` · `targets_per_run NOT NULL` · `frozen_until` · `changed_at` · `reason`. 로그 `review_source_ramp_log`: `prev_level`·`new_level`(CHECK 0~3)·`reason`·`applied_by`.
- 퍼센트 단계는 타깃 수 계단과 다른 손잡이다. 두 손잡이를 한 행에 두되 칸을 나눈다 — 기존 `level`/`targets_per_run` 은 그대로(v22 §1-3 유형별 계단 논의는 별개), 아래를 **ADD COLUMN**(비파괴, §10.2 자체 판단 범위):
  - `pct_step smallint NOT NULL DEFAULT 50 CHECK (pct_step IN (50,60,70,80,90))` — 현재 단계.
  - `cap_base integer CHECK (> 0)` — 단계 계산의 분모(§1 상한, 배분 전). **스냅샷**이다: 야간 cap 자동 상향(2배 이내)이 이 값을 따라가면 목표가 조용히 뛴다. 갱신은 사람·역할 세션 또는 block_line 재정의만.
  - `daily_request_target integer` — 오늘 목표 = floor(min(cap_base, 배분 몫) × pct_step/100). 러너가 읽는 칸.
  - `consecutive_ok_days smallint NOT NULL DEFAULT 0` · `last_evaluated_date date` — 같은 UTC 날을 두 번 세지 않는 잠금.
  - `block_line integer` · `block_line_at timestamptz` — 차단 난 날 그 소스의 그날 요청 합. 이후 `cap_base := floor(block_line × 0.9)`. 첫 요청에서 차단(block_line 1 → cap_base 0)은 자동으로 못 가고 사람 몫(소스 끄기).
  - `blocks_at_step smallint NOT NULL DEFAULT 0` — 같은 단계 차단 횟수(2회째면 동결 14일). 단계가 바뀌면 0.
  - `supply_state text CHECK (IN ('met','short','none'))` — 요약 줄용, 어제 판정.
  - 로그는 `prev_level/new_level` 재사용이 아니라 `prev_pct/new_pct smallint` 두 칸 추가(두 손잡이 이력이 섞이면 못 읽는다).
- 집행 위치(A/B): A `review_sources.daily_request_cap` 을 목표로 직접 쓴다 — §10.1 이 "2배 이내 올리기만, 내리기 금지"라 하강이 막힌다, 비권고. **B(권고)** 러너 예산 = `min(daily_request_cap, daily_request_target) − requestsToday`(`store.ts loadSource` 에 ramp 조인 1개, `runner.ts:472` budget 한 줄). cap 은 그대로 하드 상한, ramp 가 목표. 하강은 ramp 쓰기라 §10.1 '안전 되돌리기' 허용 안이다.

## 7. 위험과 남헌 결정 질문

위험
- 1. 이론 시간 ≠ 실제: 09-28 실측 소스 1건 130~489초(이론 26초). 162분 이론이 실제 300분이면 90분 타임아웃으로 뒤 소스가 interrupted — 정상이 아니라 단계가 멈추고, 앞 소스(ADAPTERS 순서상 danawa·appstore·hackernews)만 올라간다. 완화: 실제 소요(`finished_at−started_at`)를 상한에 반영하는 보정 계수는 실측 7일 뒤에 넣는다(지금은 근거 없음).
- 2. 데이터센터 IP: Actions 러너(Azure 대역)는 가정용 IP 보다 낮은 선에서 막힐 수 있다 — todayhumor 가 09-24 첫 요청부터 403 이었다. b 소스의 잠정 상한은 호스트 내성과 무관한 수요값이라 "90% 안"이 안전을 뜻하지 않는다. 차단선이 한 번 잡혀야 실측이다.
- 3. cap 이 움직인다: 야간 `review-request-cap.mjs` 가 cap 을 2배까지 올린다. cap_base 를 스냅샷으로 떼지 않으면 목표가 단계 변화 없이 뛴다(§6).
- 4. 소유자 예외 소스(appstore·googleplay) 하강 폭: v22 §1-5 는 "차단 1건 = level 0 + 14일", v25 는 "한 단계 + 3일". 둘이 충돌한다(Q5).

- 6. 차단 신호 중 '빈 응답'은 엄격 모드(소유자 예외·`abortOnChallenge`)에서만 센다(`runner.ts:570`). 다른 소스의 2xx 빈 응답은 차단으로 안 잡힌다 — 그런 소스는 연속 0건 → degraded 로만 보인다. v25 의 '빈 응답 = 차단'을 전 소스로 넓히려면 러너 한 줄 변경과 오탐(정말 글이 없는 날) 대가가 있다.
