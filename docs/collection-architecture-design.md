# 수집·학습 루프 공용 아키텍처 — 설계 판정 (2026-09-02)

소스를 다나와 하나에서 넓히고, SaaS·보험까지 카테고리를 확장하고, 두 루프를
공용 골격으로 묶을 수 있는지 검토한 기록. **설계만 했고 코드·DDL 은 실행하지
않았다.**

---

## A. 두 루프를 통합하지 않는다 — 접점 3개만 일반화한다

리뷰 수집 루프와 인사이트 루프가 겉보기에 같은 골격(수집→파생→검증→승격)을
쓰지만, **통합하면 안 되는 이유가 셋 있고 전부 코드에 근거가 있다.**

1. **권한 경계가 다르다.** `nightly-review-collect.yml` 은 `contents: read`,
   `nightly-insight-loop.yml` 은 main 커밋 권한이다. 워크플로 주석이 이미
   "권한이 다른 일을 한 잡에 합치면 낮은 쪽이 높은 쪽으로 끌려간다"고
   못박았다. 통합은 그 결정을 되돌리는 일이다.
2. **판정의 성질이 다르다.** `lib/review/health.ts` 는 "소스가 살아있는가"
   (정수 교차곱)이고, `lib/insight/patterns.ts` 의 `decide` 는 "기준선 대비
   상대 효과크기"다. 리뷰 쪽엔 승격 개념이 없고 승격은 사람이 한다.
3. **`decide()` 재사용은 조용히 무동작한다.** `decide` 는 기준선이 null 이면
   무조건 `hold` 를 돌려준다. `analysis_aspects` 에는 시계열 성과도 기준선도
   없어 **전량 hold 로 떨어지고 로그에는 "판정 완료"로 보인다** — §7.1 이
   금지한 바로 그 형태다.

**재사용 가능한 것은 `decide()` 호출이 아니라 그 안의 두 가드 형태**다 —
최소 표본(`MIN_SAMPLE=5`)과 좀비 종료(`NO_EFFECT_SAMPLE=12`). 리뷰 쪽에
옮기면 "근거 리뷰 N건 미만 속성은 승격 후보에서 제외"가 된다.
**지금은 못 옮긴다** — `analysis_aspects` 에 `evidence_count` 에 해당하는
컬럼이 없다. 비파괴 컬럼 하나로 풀리지만 채우는 주체가 extract 라우트라
로직 변경이 따라붙는다. B/C 가 닫힌 뒤로 미룬다.

일반화할 접점은 셋뿐이다 — 실행 원장, 경보 채널, 게이트 상수의 단일 출처.

## B. `review_sources` 를 분리하지 않고 컬럼으로 확장한다

`review_targets` / `review_collection_runs` / `review_fingerprints` /
`analysis_inputs` 4개 테이블의 FK 가 전부 `review_sources(key)` 하나를 본다.
테이블을 쪼개면 Postgres 에서 "둘 중 하나를 참조하는 FK"가 불가능해 지문·
타깃·실행이력이 소스 종류별로 갈라진다. **"소스 하나만 갈아끼운다"는 설계
이점이 통째로 사라진다.**

마이그레이션 초안 `20260902000001_review_source_api_mode.sql` — 신규 컬럼
9개(전부 DEFAULT 있음, 기존 danawa 1행 영향 0)와 CHECK 제약 6종. 핵심은
제약이 **정책을 DB 에 박는다**는 것이다:

- `review_sources_robots_scrape_locked` — 스크래핑 소스가 robots 검사를 끄는
  것을 DB 가 막는다
- `review_sources_api_needs_terms` — API 소스는 `terms_reviewed_at` 없이는
  INSERT 자체가 실패한다. **사람이 ToS 를 읽은 기록이 곧 승인 기록이다**
- `review_sources_units_need_cap` — units 쿼터인데 한도가 없으면 실패
- `auth_env_key` 는 **키가 아니라 환경변수 이름**만 담는다 (CLAUDE.md §2)

### 🔴 API 소스에서 지금 구조가 깨지는 지점 — 가장 실질적인 위험

- **`daily_request_cap` 은 요청 수를 센다.** YouTube Data API 는 엔드포인트마다
  유닛 비용이 다르다. 요청 수 상한만으로는 실제 쿼터를 훨씬 빨리 태운다
- **쿼터 소진이 403 으로 온다.** `lib/review/health.ts` 는 403 을 무조건
  차단으로 읽고 `broken` + `enabled=false` 를 내린다. 즉 **정상적인 쿼터
  소진이 "차단당했다"로 기록되고 소스가 꺼진다.** §7.1 이 실패 쪽에서
  재발하는 형태다
- **쿼터 창이 UTC 자정 고정이다**(`store.ts:38`). API 제공자의 리셋 시각대와
  어긋나면 한도를 두 번 소비하는 날이 생긴다
- **`nextRequest` 가 `{ url }` 만 반환한다.** 네이버 API 는 인증 헤더가
  필수라 지금 인터페이스로는 못 담는다. 어댑터가 `process.env` 를 직접 읽게
  하면 픽스처 테스트가 환경 의존이 되므로, 러너 포트로 주입해야 한다

## C. pgvector 는 지금 도입하지 않는다

**리뷰 1건당 임베딩(1536차원) 6.0KB 는 그 리뷰 원문(약 0.5KB)의 12배다.**
원문을 30일 뒤 지우면서 파생물 6KB 를 무기한 보관하는 건 자기모순이다.

| 항목 | 1건 | 4천건 | 1만건 | 10만건 |
|---|---|---|---|---|
| 원문(`analysis_inputs`) | 0.5KB | 2MB | 5MB | 50MB |
| 지문(인덱스 3개 포함) | 0.45KB | 1.8MB | 4.5MB | 45MB |
| 임베딩 1536차원(+HNSW) | 6.0KB | 55MB | **130MB** | **1.3GB** |
| 임베딩 384차원(+HNSW) | 1.5KB | 14MB | 33MB | 330MB |

- **10만건은 1536/768 차원 모두 무료 500MB 에서 불가능하다.**
- 도입한다면 대상은 리뷰 원문이 아니라 `analysis_aspects.name` /
  `insight_patterns.pattern_key`(합계 1천 행 미만, 6MB, 인덱스 불필요)다
- **새 과금이 붙는다.** Anthropic 은 임베딩 모델을 제공하지 않아 외부
  프로바이더 계약이 새로 필요하다

### §4.5 의 지문 용량 추정이 틀렸다

"행당 120바이트 / 연 2.2MB"로 적혀 있는데, `identity_key`+`content_hash` 만
sha256 hex 64자 × 2 = 128바이트다. 행 헤더·uuid·timestamptz 2개·인덱스 3개를
더하면 실효 약 450바이트, **연 8MB** 다. 결론(무해)은 안 바뀌지만 숫자는
정정한다.

### 30일 폐기의 진짜 근거는 용량이 아니다

현 스코프에서 원문+지문 전량이 4MB, 티어의 0.8% 다. **500MB 압박은 실재하지
않는다.** 폐기 근거를 "용량"으로만 적어 두면 나중에 "안 지워도 되네"로
뒤집힌다. 실질 근거는 **데이터 위생 — 남의 리뷰 원문을 무기한 보관하지
않는다** 이고, §9 를 그렇게 고치는 게 맞다.

### 티어 근접 사전 경고 — §7.1 준수 조항 3개

야간 인사이트 루프 요약 최상단, `sourceAlerts` 와 같은 규약(정상이면 줄
자체가 없다). 임계는 절대(60/75/85%) + 추세(잔여일) 2축.

- `storage_report()` RPC 가 없거나 권한 오류면 **"용량 확인 불가"를 경보로
  올린다.** 조용히 넘기지 않는다
- 스냅샷이 1건 이하면 "추세 판정 불가". 증가량 0 으로 읽지 않는다
- 한도값은 env 로 받고, 미설정이면 비율 판정을 하지 않고 "한도 미설정 —
  판정 불가"로 보고한다. **500MB 를 코드에 박지 않는다**

## D. SaaS·보험에서 깨지는 건 스키마가 아니라 소스다

먼저 **설계문서 §12 선행조건 2가 해소됐다.** `quadrant` 는 프롬프트도 SQL 도
아니고 `app/api/analyze/review/route.ts:36` 의 `computeQuadrants` 가
**프로젝트 내부 중앙값 분할**로 계산해 UPDATE 한다. `opportunity_score` 만
SQL generated 다. 즉 **두 값은 기준이 다르다** — 하나는 절대값(0~20), 하나는
프로젝트 내 상대순위.

스키마 쪽 실제 파손 지점:

1. **중앙값 분할은 항상 사분면을 채운다.** 모든 속성이 만족스러운 제품에서도
   절반이 `DIFFERENTIATOR` 가 된다. "중요한데 아무도 못 채운 속성"이라는
   해석이 성립하지 않는다
2. **동률이 `DIFFERENTIATOR` 로 쏠린다.** SaaS 는 속성 수가 적고(기능·가격·
   지원·온보딩·연동) 만족도가 뭉치는 경향이라 동률이 흔하다
3. **`opportunity_score` → `content_items.tier` 매핑이 카테고리 간 비교를
   전제한다.** `importance` 가 빈도 기반이라 카테고리가 다르면 같은 8점이
   같은 것을 뜻하지 않는다. 절대 구간이 아니라 프로젝트 내 백분위여야 한다
4. **보험에서 빈도 기반 `importance` 가 구조적으로 어긋난다.** 가장 중요한
   속성(청구 지급 여부)은 사고를 겪은 소수만 쓴다
5. **`pain_timing` 이 두 값뿐이다.** SaaS 의 도입·갱신, 보험의 청구가 전부
   `POST_PURCHASE` 로 뭉개진다. 값 추가는 비파괴다
6. **`attribution` 에 중개자가 없다.** 보험 설계사·SaaS 벤더 지원 조직이
   어디에도 안 맞고, `pickEnum` 이 미허용 값을 **조용히 null 로 만든다**
7. **살아있는 것도 있다.** `persona_role` 은 소비재에서 네 값이 같은 사람으로
   붕괴하는데 SaaS B2B 에서는 실제로 분리된다 — **소비재보다 SaaS 에서 더 잘
   작동한다**
8. **`pickScore` 가 0~10 clamp 를 하지만 감지는 안 한다.** 1~5 척도 출력을
   압축할 뿐이고, 범위 CHECK 가 DB 에도 없다

**결정적 병목은 소스다.** `analysis_inputs.source_key` FK 가 `review_sources`
를 보므로 새 소스 등록 없이는 SaaS 리뷰를 한 행도 못 넣는다. 스키마 논의보다
소스 확보가 먼저다 → `docs/review-source-findings.md` 2차 실측 참조.
