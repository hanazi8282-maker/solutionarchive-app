  2. 코드 변수(환경 변수)의 관행은 **GitHub 리포 변수 `vars.X || '기본값'`을 워크플로 `env:`에 꽂고, 스크립트는 `process.env.X`로 읽는다**(C-4).

### Q1. discovery_candidates 를 만드는 곳, 시험 소스가 hackernews 뿐인 이유, 합격 → review_targets

- 만드는 곳이 **셋**이다.
  1. `scripts/discovery-run.mjs`(크론 nightly-discovery.yml, KST 02:13). 후보는 `claude -p`가 이름만 내고(`propose`, :260~), 코드가 `screen`·`judge`(lib/discovery/candidate.ts)로 거르고 **프로브가 센 hits 가 채택을 정한다**.
  2. 언급 루프 `lib/discovery/mention-loop.ts:576~592`(SQL 초안 INSERT 문을 만든다. 직접 INSERT 는 하지 않는다).
  3. 신작 `scripts/new-release-ledger.mjs:39~44`(역시 SQL 초안).
- **hackernews 로만 가는 이유**: `scripts/discovery-run.mjs:77` 에 `const PROBE_SOURCE = { physical: 'danawa', saas: 'hackernews' }` 로 **축마다 시험 소스가 한 개로 하드코딩**돼 있다. `kind=saas`이면 `probeSaas`(lib/discovery/probe.ts:151~168)가 HN Algolia `nbHits`를 센다. 코드가 만드는 `probe_ref` 는 `q:<이름>` 이다. 앱스토어·깃허브·구글플레이를 시험하는 경로 자체가 없다. 컬럼 `probe_source_key`는 `review_sources(key)` FK 이다(마이그 `20260921000001_discovery_candidates.sql:33`). 즉 FK 때문이 아니라 코드 때문이다.
- **합격 후보 → 타깃**: 같은 파일 `persist()`(:465~535).
  - 합격(`accepted`)이 아니면 후보만 기록.
  - 합격이면 `review_sources.enabled` 를 확인(꺼져 있으면 `unverified`+`source_disabled`로 기록하고 끝).
  - 켜져 있으면 `analysis_projects` INSERT(`status='collecting'`, SaaS는 `business_model='SAAS'`) → `review_targets` INSERT(`source_key=probeSourceKey`, `product_ref=q:<이름>`, `status='active'`, `cursor=null`) → `discovery_candidates` INSERT(`project_id` 연결).
  - 이 쓰기 범위가 CLAUDE.md §10.1 "발굴 적재"의 허용 범위다.
- 새 소스로 보내려면: `PROBE_SOURCE`를 축당 하나에서 "후보당 시험 경로 목록"으로 바꿔야 하고, `persist()` 의 `product_ref` 규칙(`q:` 접두)을 소스별로 갈라야 한다(앱스토어는 `kr:<id>`, 구글플레이는 `kr:ko:<pkg>`). 신작 쪽은 이미 `probe_source_key: 'appstore'|'googleplay'|'shopify_apps'`를 쓰고 있다(new-release-ledger.mjs:21~32) — 이 부분을 재사용한다.

### Q2. mention·new_release 행이 왜 10-22·10-18 이후 없나

- **크론에서 빠진 것이 아니다.** mention-loop-nightly.yml(`41 23 * * *`)과 new-release-nightly.yml(`17 0 * * *`)은 둘 다 매일 돈다.
- **그러나 둘 다 `permissions: contents: read` 이고 "write report files only"** 이다. 하는 일은 `reports/<날짜>/*.sql`(`new-release-ledger.sql`, 롤백 SQL)과 `mention-*.json`을 **아티팩트로 올리는 것**(retention 14일)까지다. DB INSERT 도, 리포 커밋도 없다.
- 행이 생기려면 사람(세션)이 그 SQL 초안을 마이그레이션으로 만들어 적용해야 한다. 10-22 행은 `20261022000030_mention_ledger_20261021.sql` 이 그 수작업 산출물이다. 10-18 신작도 같은 구조다. **그 이후 아무도 안 넣었다 = 행 없음.** 즉 "실패"가 아니라 "마지막 다리가 사람 손"이다.
- 이름이 일반 명사(`table`, `data`)인 것: 언급 추출 후 제외 목록·제품 확인이 약하다(mention-loop.ts 안 `PRODUCT_NAME` 계열 처리 — S7 에서 확인 필요).

- 마지막 크론 성공 여부(실행 기록)는 GitHub Actions 쪽 확인 필요 — DB 아님.

### Q4. exhausted 가 되는 조건, 재방문 규칙

`exhausted` 로 바뀌는 곳은 **러너에 4군데**, 그 밖에 SQL 두 곳이다. (`lib/review/runner.ts`)

1. 비증분형 소스는 끝까지 읽으면(`nextCursor=null`) `endStatus='exhausted'`(:613, 커서도 비움). 앱스토어 RSS·다나와·유튜브 영상이 여기다.
2. robots 가 금지·확인 불가이면 `status='exhausted'`(:695 부근, 요청 안 보냄).
3. **증분형(HN·구글플레이·게시판 등)은 연속 0건으로 닫는다**: `closeAfter` = 글 `MAX_CONSECUTIVE_EMPTY=3`(health.ts:35), 게시판 `BOARD_MAX_CONSECUTIVE_EMPTY=30`(health.ts:43). 조건 `adapter.incrementalOnly ∧ !dryRun ∧ !aborted ∧ status==='active' ∧ consecutiveEmpty >= closeAfter`(:925~931).
4. 창문 강등(scripts/window-discovery.mjs)과 게시판 강등 SQL: 등재 3일 뒤 신규 0 → `exhausted`.

재방문(되살리기) 규칙: `scripts/target-revive.mjs --auto`가 `nightly-review-collect.yml` 수집 직전 스텝으로 돈다. 로직은 `lib/review/target-supply.ts`.
- `revisitDays()`(:522~): 비증분형만. `λ = min(총수집/경과일, 1/(마지막방문−마지막리뷰일))`, `days = clamp(3 ÷ λ × 2^consecutive_empty, 3, 14)`. λ=0 이면 14일.
- 증분형은 간격 규칙이 없어 `opts.all` 일 때만 같은 식을 쓴다. 연속 0건 3회(글)·30회(게시판)로 닫히므로 `2^ce` 가 8배 이상 → 거의 전부 14일 상한(주석 :457~).
- 소스별 손잡이(리포 변수): `TARGET_REVISIT_SCALE`(0.25~1, 줄이기만), `TARGET_REVIVE_CE_EXP_MAX`, `TARGET_REVIVE_QUEUE_SLACK`.
- 제외: `SUPPLY_EXCLUDED`(target-supply.ts:58 = 램프 제외 + producthunt, danawa·todayhumor 포함), robots 금지 확정 소스, 꺼진 소스.
- **v71cu S2 의 "연속 빈 횟수 n → 간격 ×2^n, 휴면" 은 이미 "되살리기 쪽에는" 있고, "방문 선택 쪽(listDueTargets)"에는 없다.** 방문 선택은 `status='active'` 를 `last_run_at` 오름차순으로 뽑을 뿐이다(C-1). `next_visit_at` 칸은 오늘 마이그 `20261119000002_ss_target_visit_columns.sql` 로 막 생겼고 읽는 코드는 아직 없다(`grep next_visit_at lib` = 0).
- 보충: 설계서가 말한 "연속 30회 빈 클리앙 cm_venture 가 그대로"는 게시판 문턱이 30이고 `exhausted` 로 닫혀도 되살리기가 다시 `active` 로 올리기 때문이다(revive 가 되살려 도로 30회 반복).

### Q5. 구글 플레이 다음 장 처리 — 왜 첫 장에서 끝나나

  - 데이터: 티로·비토처럼 44·43건에서 끝난 앱이 **실제로 그 로케일에 리뷰가 그만큼뿐인지**는 코드로 못 가른다 → DB 확인 필요(예: 같은 앱 `us:en` 건수, 마지막 실행의 `outcome` 문구 `review_collection_runs`).
- S3 에 필요한 한 줄: 옛 쪽(`back`) 커서를 따로 저장할 칸이 없다. `review_targets.cursor` 하나뿐이고, 그 칸의 의미가 "증분형은 매 실행 최신부터"로 고정돼 있다. 새 칸 또는 `cursor` JSON 으로 `{head, back}` 를 담아야 한다. 게시판 어댑터는 이미 `cursor` 에 JSON 을 담는다(`decodeBoardCursor`, lib/review/types.ts).

### C-3. 어댑터 인터페이스 — `listPage(cursor)` 를 더하려면

`lib/review/types.ts:212` `ReviewSourceAdapter`:
- `nextRequest(target: TargetState): ReviewRequest | null` — URL 계산만, **네트워크 금지**(:216~224).
- `parse(body, ctx: ParseContext): ParseResult` — 순수 함수. `ParseResult = { reviews, nextCursor, parseFailures, filtered?, missing?, pauseRun? }`(types.ts:139~). `ParseContext` 에 `cursor`, `lastReviewAt`, `productRef` 가 있다.
- 선택 필드: `incrementalOnly`, `maxPagesPerRun`, `abortOnChallenge`, `quotaMarkers`, `blockStatuses`, `proceedWhenRobotsUnverified`, `skipNotFound`, `isChallenge`, `requiredEnv`, `productScopedExternalId`.
- 즉 지금 어댑터는 **`nextRequest(커서 포함 상태) → 러너가 fetch → parse(→nextCursor)`** 의 2단 구조이고, 러너가 robots·간격·상한·커서 저장(페이지마다 `saveTargetProgress`, runner.ts:~800)을 한다. `listPage(cursor) → {items, nextCursor, oldestAt}` 는 이 구조의 **다른 이름**이다: `nextRequest` ≈ 요청 만들기, `parse` ≈ `{items=reviews, nextCursor}`. `oldestAt` 만 없다(`ParseResult` 에 `reviews[].writtenAt` 의 min 으로 계산 가능).
- 권고(최소 변경): `listPage` 라는 새 메서드를 만들지 말고 (1) `ParseResult` 에 `oldestAt?: string | null` 을 더하고 (2) `review_targets.cursor` 를 `{head,back}` JSON 으로 확장(게시판 어댑터가 이미 `encodeBoardCursor`/`decodeBoardCursor` 를 쓰는 선례, types.ts) (3) 러너의 `resetAtCap`(:~891)와 `emptyClose`(:925)가 `back` 커서가 남아 있으면 닫지 않게 고친다. 기존 `cursor` 문자열은 `decode` 에서 "문자열이면 head 로 본다"로 읽으면 하위 호환이다.
- 어댑터 파일은 `lib/review/adapters/*.ts` 29개. 구글플레이는 :124 `nextRequest`, :135 `parse`.

### C-4. 변수(환경 변수) 관행 — 새 변수 두는 곳

- **GitHub 리포 변수(`vars.X`)를 워크플로 `env:` 에서 `${{ vars.X || '기본값' }}` 로 꽂고**, 스크립트는 `process.env.X`(빈 문자열은 미지정, `||` 로 받는다)로 읽는다. 예: nightly-relevance.yml:111~140(`RELEVANCE_*`, `LLM_DAILY_BUDGET_USD`), nightly-discovery.yml(`DISCOVERY_TARGET`, `DISCOVERY_MIN_VOC_HITS`…), 창문 등재 `DISCOVERY_TARGET_MAX`.
- JSON 객체 변수의 파서 선례: `parseRevisitScale`·`parsePerSourceInt`(lib/review/target-supply.ts:455~500) — 소스별 값에 쓴다. 범위 밖은 그 항목만 버리고 note.
- 코드 안 값(구독 한도 %·달러 환산)은 `config/session-guard.json`(읽는 곳 `lib/analysis/session-guard.ts`), 기한이 붙는 값은 같은 파일의 `*_until`.
- 배치 이름으로 켜고 끄는 값은 DB 칸(`review_targets.onboard_batch`)과 변수 `COLLECT_ONBOARD_DISABLED_BATCHES` 조합.
- 새 변수 제안 위치:
  - `JUDGE_DAILY_ITEMS_FIRST`·`JUDGE_DAILY_ITEMS_SECOND`·`JUDGE_BACKLOG_ALERT` → **기존 이름 `RELEVANCE_*` 와 매핑**(`RELEVANCE_SAMPLE × RELEVANCE_MAX_PROJECTS` ≈ 1차 건수, `RELEVANCE_SECOND_MAX` = 2차). 같은 뜻의 변수가 이미 있어 새 이름으로 병행하면 두 개가 갈라진다. 이름을 `JUDGE_*` 로 하겠다면 `nightly-relevance.yml` env 줄 하나(`RELEVANCE_SECOND_MAX: ${{ vars.JUDGE_DAILY_ITEMS_SECOND || vars.RELEVANCE_SECOND_MAX || '200' }}`)로 alias 한다.
  - `JUDGE_DAILY_USD_CAP`·`JUDGE_MONTHLY_USD_CAP` → `lib/analysis/budget.ts`(현재 `LLM_DAILY_BUDGET_USD` 읽는 곳)와 같은 방식. 단 claude-cli 는 미계량이라 전제부터 새로 만든다(Q10).
  - `COLLECT_*`·`YT_*` → `nightly-review-collect.yml` 의 수집 스텝 env 에 `vars.COLLECT_…` 로 꽂고 `scripts/review-collect.mjs` 또는 `lib/review/ramp.ts` 가 읽는다. `COLLECT_NEW_SOURCES_PAUSED`·`COLLECT_ONBOARD_DISABLED_BATCHES` 는 C-1 의 `due()`·`googlePlayDue()` 두 군데에서 `onboard_batch` 제외로 쓴다. `YT_*` 는 `lib/review/adapters/youtube.ts` 쪽.
