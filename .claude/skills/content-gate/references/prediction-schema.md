# 예측 스키마 (Prediction Schema) — 자동 채점 규격

> **성격**: 판정 로그의 `예측`을 **기계가 채점할 수 있는 형태**로 정의한다.
> **위치**: `methodology/content/prediction-schema.md`
> **소비처**: `solfa/04-decisions.md` · `pdp/04-decisions.md` 판정 로그 / `scripts/score-predictions.mjs`
> **왜 필요한가**: 이게 없으면 D+7에 사람이 매번 판정해야 하고, 그러면 루프가 안 돈다

---

## 0. 이 파일이 존재하는 이유 — 닫힌 루프의 마지막 조각

목표는 이 루프다.

```
스킬이 초안 생성
   ↓
게이트 통과 (판정 + 지문 + 예측 기록)
   ↓
발행  ← 사람의 승인. §10 정책상 자동 발행 금지
   ↓
데이터 수집 (Threads metrics, 1h/24h/168h)
   ↓
예측 vs 실측 자동 채점        ← ★ 이 파일이 정의하는 것
   ↓
규칙별 신뢰도 갱신
   ↓
무효 3건 누적 시 갱신 후보 자동 생성
   ↓
자가 문항 생성 (eval-set 자동 확장)
   ↓
스킬 갱신 → 회귀 검사(eval) → 배포
```

앞뒤는 이미 있다. Threads API 토큰과 metrics collector(1h/24h/168h 스냅샷), 각 아카이브 각 아카이브 04-decisions의 예측·지문 칸. **없는 건 예측과 실측을 기계가 대조하는 부분**이다.

지금 예측은 자연어다.
```
예측: "저장률이 평소보다 높을 것. 정보 밀도가 높아 나중에 다시 볼 이유가 있기 때문"
```
사람은 읽지만 기계는 못 채점한다. **"평소"가 무엇인지, "높다"가 얼마나인지 정의가 없다.**

## 1. 지표 정의

### 1-1. 우선순위 (남헌 확정 2026-09-04 → **2026-09-05 재조정**)

```
좋아요율 > 공유율 > 답글율 > 조회수
```

> **[2026-09-05 변경] `save_rate` 를 우선순위에서 뺐다.** Threads API 가
> `saves` 를 주지 않는 것이 실호출로 확정됐다(§7-2). 원래 1순위 지표였고
> 가중치 8이었다. 이 줄을 지우지 않는 이유는, 지우면 다음 사람이 "왜 저장률이
> 없지"를 다시 조사하기 때문이다. **없어서 뺀 것이지 안 중요해서 뺀 게 아니다.**
>
> ⚠️ 이 문서 **아래쪽 예시(§3·§4·§6·§9)는 아직 `save_rate` 를 쓴다.** 예시는
> 스키마 문법을 보여주려고 쓴 것이고 §6 지문은 평가 문항이 원문 실측에 묶여
> 있어 손대지 않았다. **실제 예측을 쓸 때는 `save_rate` 를 `like_rate` 로
> 읽어라.** 예시를 그대로 복사하면 전부 `보류`로 빠진다.

**모두 비율(rate)로 본다.** 원시 카운트가 아니다.

| 지표 | 계산식 | 가중치 | 근거 |
|---|---|---|---|
| **`like_rate`** | `likes / views` | **8** | 즉각 반응. 노이즈 있으나 표본이 크다 |
| **`share_rate`** | `(reposts + quotes) / views` | **4** | 솔파 §2-9 4번(공유 이유)의 실측치 |
| **`reply_rate`** | `replies / views` | **2** | 논란·질문형. 보조에서 승격됐다 |
| **`views`** | 원시 카운트 | **1** | 도달. 단독으로는 판정 근거로 약함 |

~~`save_rate` = `saves / views` (가중치 8)~~ — **API 미제공. 사용 금지.**
쓰면 분자가 영원히 없어서 전부 `보류`로 빠진다.

**왜 비율인가**: 조회수는 로그정규 분포에 가까워서 단일 건 비교가 거의 무의미하다. 비율로 바꾸면 **도달 편차가 상쇄**되고 콘텐츠 자체의 반응 강도만 남는다.

**보조 지표** (예측에 쓸 수 있으나 우선순위 밖)

| 지표 | 계산식 | 용도 | 가용성 (2026-09-05 실호출) |
|---|---|---|---|
| `click_rate` | `clicks / views` | 전환 목적 콘텐츠. **유일하게 새로 쓸 수 있는 지표** | ✅ 미디어·계정 양쪽 |
| ~~`profile_ctr`~~ | ~~`profile_visits / views`~~ | 가치 사다리 다음 계단 진입 (프드프 §8-6) | ❌ `profile_visits` 없음 |
| ~~`nonfollower_ratio`~~ | ~~`nonfollower_views / views`~~ | 솔파 §9-3 비구독자 90% 치환 | ❌ `nonfollower_views` 없음 |
| ~~`link_ctr`~~ | ~~`link_clicks / views`~~ | 전환 목적 콘텐츠 | ❌ `link_clicks` 없음. `clicks` 로 대체 |

> **`clicks` 는 반환되지만 아직 전부 0 이다.** [2026-09-05 실측]
> 내 계정 최근 글 12개에 `metric=views,clicks` 를 직접 걸어 봤다. 12개 모두
> `clicks=0` 이었다 (조회 1,868 짜리 글 포함). 필드 자체는 200 으로 돌아오고
> 내부 이름은 `threads_media_clicks` 다 — 계정 단위 `profile_clicks` 와 다른 값이다.
>
> 그래서 지금 알 수 있는 것은 **"API 가 준다"까지**다. **"이 계정에서 실제로
> 값이 붙는다"는 아직 확인되지 않았다.** 링크를 넣은 글이 없어서 0 인 것인지,
> 이 계정에서는 채워지지 않는 지표인지 구분할 수 없다 (CLAUDE.md §7.1 — 확인 불가).
> `click_rate` 를 판정 지표로 쓰기 전에 **링크가 든 글 하나로 0 이 아닌 값을
> 한 번 보고 나서** 쓴다.

> **`profile_visits` 는 저장 프록시로 쓸 수 없다.** §7-2 의 프록시 제안은
> "`profile_visits` 가 있으면"이 전제였는데, 실호출 결과 그 필드 자체가 없다.
> 제안을 채택한 게 아니라 **닫았다**. `clicks` 는 프로필 방문이 아니라
> 본문 링크·첨부 클릭이라 "나중에 다시 보겠다" 신호가 아니다. 프록시로 쓰지 마라.

⚠️ **분모가 0이면 판정 불가.** `views < 100`이면 자동 `보류` 처리한다(표본 부족).

## 2. 기준선(baseline) 정의

**"평소보다"의 정체.** 이게 예측 스키마의 핵심이다.

### 2-1. 기준선 종류

| 코드 | 정의 | 언제 쓰나 |
|---|---|---|
| **`median_last_k`** | 직전 K건의 중앙값 (기본 K=10) | **기본값.** 계정의 최근 평균 상태 |
| `median_format_k` | **같은 형식**의 직전 K건 중앙값 | 형식별 편차가 클 때 (캡션형 vs 기획형) |
| `median_all` | 계정 전체 중앙값 | 표본이 적을 때 폴백 |
| `absolute` | 절대값 지정 (`save_rate > 0.03`) | 외부 벤치마크가 있을 때 |
| `paired` | 지정한 특정 발행 건과 1:1 비교 | A/B 성격의 실험 |

**중앙값을 쓰는 이유**: 평균은 이상치(한 건 대박) 하나에 무너진다. 콘텐츠 성과는 이상치가 정상이다.

### 2-2. 유의미 임계

단순 대소 비교는 노이즈에 걸린다. **MAD(중앙값 절대편차)** 기준을 쓴다.

```
MAD = median(|xᵢ − median(x)|)
유의미 = |실측 − 기준선| ≥ threshold × MAD
```

| threshold | 의미 | 언제 |
|---|---|---|
| **`1.0mad`** | **기본값.** 노이즈를 넘는 최소선 | 대부분 |
| `1.5mad` | 보수적. 확실한 차이만 | 규칙 갱신을 유발할 판정 |
| `0.5mad` | 민감. 약한 신호도 잡음 | 탐색적 실험 |
| `20pct` | 상대 비율 지정 | MAD가 0일 때 폴백 |

⚠️ **MAD가 0이면**(직전 K건이 전부 동일값 — 표본 부족 시 발생) 자동으로 `20pct`로 폴백한다.

### 2-3. 부트스트랩 단계 — 표본이 없을 때

**첫 10건은 기준선이 없다.** 이 구간의 처리를 명시한다.

| 발행 누적 | 처리 |
|---|---|
| **1 ~ 4건** | 예측은 기록하되 **자동 `보류`**. 채점하지 않음 |
| **5 ~ 9건** | `median_all` + `20pct` 임계로 **참고 판정**(신뢰도 계산에서 가중치 0.5) |
| **10건 이상** | `median_last_10` + `1.0mad`. **정식 판정** |

> ⚠️ 부트스트랩 구간의 판정을 규칙 갱신 근거로 쓰지 않는다. **"찾지 못함"과 "확인 결과 음성"을 구분한다**(CLAUDE.md §7.1)는 규약이 여기에도 적용된다 — 표본이 없어서 판정 못 한 것과, 판정했는데 무효인 것은 다르다.

## 3. 예측 스키마 (정식 포맷)

### 3-1. 구조

```yaml
예측:
  - metric: save_rate          # §1-1의 지표 코드
    direction: up              # up | down | within
    baseline: median_last_10   # §2-1
    threshold: 1.0mad          # §2-2
    horizon: h168              # §1-2
    because: R-11              # 귀속 규칙 코드 (R-xx / P-xx / C-xx / 신규)
    rationale: "타깃을 넓힌 카피라 관심 없던 층까지 저장할 것"
```

**여러 지표를 걸 수 있다.** 그 경우 §4-3의 복합 판정 규칙을 적용한다.

### 3-2. 필드 정의

| 필드 | 필수 | 값 | 설명 |
|---|---|---|---|
| `metric` | ✅ | §1-1 코드 | 무엇을 측정하나 |
| `direction` | ✅ | `up` / `down` / `within` | 어느 방향. `within`은 구간 유지(예: 터지면 안 되는 계정, P-04) |
| `baseline` | ✅ | §2-1 코드 | 무엇과 비교하나 |
| `threshold` | ✅ | §2-2 코드 | 얼마나 차이나야 유의미한가 |
| `horizon` | ✅ | `h1` / `h24` / `h168` | 언제 측정하나 |
| `because` | ✅ | 규칙 코드 | **이 예측을 만든 판정.** 신뢰도가 여기로 귀속된다 |
| `rationale` | ✅ | 자연어 1줄 | 사람이 읽는 근거. 채점에는 안 쓰임 |
| `k` | — | 정수 | `median_last_k`의 K. 생략 시 10 |
| `format` | — | 문자열 | `median_format_k`용 형식 태그 |
| `value` | — | 숫자 | `absolute` baseline의 목표값 |
| `paired_with` | — | LOG 코드 | `paired` baseline의 비교 대상 |

### 3-3. `direction: within` — 터지면 안 되는 경우

프드프 P-04(터지면 안 되는 계정)를 자동 채점하려면 필요하다.

```yaml
예측:
  - metric: views
    direction: within
    baseline: absolute
    value: [3000, 30000]      # 하한, 상한
    horizon: h168
    because: P-04
    rationale: "브랜딩 목적. 대중 도달은 오히려 손해"
```

**상한을 넘어도 `무효`다.** 조회수가 많이 나온 게 성공이 아니라는 걸 기계가 알아야 한다.

### 3-4. 나쁜 예 / 좋은 예

| ❌ 나쁜 예측 | 왜 |
|---|---|
| `"반응이 좋을 것"` | 지표·기준·임계 전부 없음 |
| `"저장이 많이 될 것"` | 원시 카운트. 도달 편차에 오염됨 |
| `"평소보다 높을 것"` | "평소"의 정의 없음 |
| `metric: views, direction: up` (단독) | 우선순위 최하위 지표 단독. 판정 근거로 약함 |

| ✅ 좋은 예측 |
|---|
| `save_rate / up / median_last_10 / 1.0mad / h168 / because: R-11` |
| `views / within / absolute [3000,30000] / h168 / because: P-04` |
| `share_rate / up / median_format_5 / 1.5mad / h24 / because: C-12` |

## 4. 자동 채점 규칙

### 4-1. 단일 지표 판정

```
1. horizon 시점의 metrics 스냅샷을 가져온다
2. views < 100 이면 → 보류 (표본 부족)
3. baseline을 계산한다 (부트스트랩 단계면 §2-3 적용)
4. MAD를 계산한다. 0이면 20pct 폴백
5. delta = 실측 − 기준선
6. 판정:
   direction: up     → delta ≥ threshold × MAD          이면 유효
   direction: down   → delta ≤ −(threshold × MAD)        이면 유효
   direction: within → value[0] ≤ 실측 ≤ value[1]        이면 유효
   그 외 → 무효
7. |delta| < threshold × MAD 이고 direction이 up/down이면 → 보류
   (방향이 틀린 게 아니라 차이가 노이즈 범위)
```

⚠️ **`무효`와 `보류`를 구분한다.** 방향이 반대면 무효, 차이가 노이즈 범위면 보류다. 이걸 섞으면 규칙 신뢰도가 오염된다.

### 4-2. 산출 예시

```
LOG-20260910-01
  예측: save_rate / up / median_last_10 / 1.0mad / h168 / because: R-11
  실측: save_rate = 0.0312
  기준선: 0.0190 (직전 10건 중앙값)
  MAD: 0.0061
  delta: +0.0122  =  +2.00 MAD
  판정: 유효 ✅  (임계 1.0 MAD 초과)
  → R-11 신뢰도 +1
```

### 4-3. 복합 판정 (여러 지표를 걸었을 때)

**가중 다수결.** §1-1의 가중치를 쓴다.

```
score = Σ (가중치 × 판정값)     판정값: 유효 +1 / 무효 −1 / 보류 0
score > 0  → 유효
score < 0  → 무효
score = 0  → 보류
```

**예**: `save_rate 유효(+8)` + `views 무효(−1)` → `score = +7` → **유효**
→ 저장률이 올랐으면 조회수가 좀 떨어져도 성공으로 본다. 우선순위 반영.

### 4-4. 지문 대조 (선택)

`지문` 필드가 있으면 채점 결과에 함께 기록한다. **판정이 무효일 때 지문을 보면 "무엇을 근거로 그렇게 판단했는지"가 남아 있다.** 이게 규칙 갱신의 원재료다.

## 5. 규칙 신뢰도 계산

### 5-1. 집계

각 LOG 엔트리는 `because`로 규칙에 귀속된다. 규칙별로 누적한다.

```
R-11:  유효 7 / 무효 1 / 보류 3
```

### 5-2. 신뢰도 = Wilson score 하한

단순 비율(`유효/(유효+무효)`)은 **표본이 적을 때 과신**한다. 1승 0패면 100%가 되어버린다.

```
Wilson lower bound (95% 신뢰수준)
n = 유효 + 무효
p = 유효 / n
z = 1.96

lower = (p + z²/2n − z·√(p(1−p)/n + z²/4n²)) / (1 + z²/n)
```

| 실적 | 단순 비율 | **Wilson 하한** |
|---|---|---|
| 1승 0패 | 100% | **21%** |
| 7승 1패 | 88% | **53%** |
| 20승 3패 | 87% | **68%** |

**보류는 분모에 넣지 않는다.** 판정을 못 한 것이지 틀린 게 아니다.

### 5-3. 자동 액션

| 조건 | 액션 |
|---|---|
| **무효 3건 누적** | 해당 아카이브 04-decisions §3에 **`UPD-` 갱신 후보 자동 생성** |
| Wilson 하한 < 30% (n≥5) | ⚠️ 규칙 자체를 의심. 재검토 플래그 |
| 유효 10건 + 하한 > 70% | ✅ 안정 규칙. 게이트에서 우선 적용 |
| 보류 비율 > 50% (n≥10) | 예측 설계가 잘못됨. **지표나 임계를 바꿔야 함** |

> 마지막 항목이 중요하다. 보류가 많다는 건 규칙이 틀린 게 아니라 **측정이 틀린 것**이다.

## 6. 자가 문항 생성 (eval-set 자동 확장)

### 6-1. 언제 생성하나

| 조건 | 문항 유형 |
|---|---|
| **정방향 판정이 `무효`** | 예측과 실측이 갈림. **정답 = 실측** |
| **역방향에서 "한쪽만 탈락"** | 조건부 규칙의 증거 (C-xx 갱신 대상) |
| **역방향에서 "둘 다 탈락"인데 터짐** | 양쪽 규칙의 공통 구멍 |

### 6-2. 생성 포맷

```markdown
### Q31. [자동생성 LOG-20260910-01]
아래 두 글 중 어느 쪽의 저장률이 높았나?
- A: (이 발행 건의 카피 첫 문장)
- B: (직전 10건 중 중앙값에 해당하는 건의 카피)

정답: B  (실측 save_rate: A 0.008 vs B 0.019)
근거: R-11을 적용해 타깃을 넓혔다고 판단했으나, 실제로는 카피가 넓기만 하고
      본문이 좁아서 저장 이유가 안 생김. → R-11의 "카피와 본문 층위 분리" 조건 누락
출처: 자체발행 (원문 아님)
```

⚠️ **자동 생성 문항은 `[자동생성]` 태그를 단다.** 원문 기반 30문항과 구분해야 한다 — 원문 문항은 정답이 검증된 것이고, 자동 생성은 **내 데이터가 정답지**다.

### 6-3. 정답지의 이동

```
시작:    30문항, 정답 출처 = 솔파·프드프 원문
6개월 후: 100문항, 그중 70문항의 정답 출처 = 내 발행 실측
```

**이 비율이 곧 오리지널리티 좌표다.** 각 아카이브 04-decisions §6의 "덮여쓴 규칙 수 / 14"와 같은 현상을 다른 각도에서 측정한다.

## 8. 실패 모드와 방어

| 실패 모드 | 증상 | 방어 |
|---|---|---|
| **보류 폭증** | 판정의 50%+가 보류 | §5-3 마지막 항목. 지표·임계 재설계 |
| **기준선 오염** | 대박 1건이 중앙값을 밀어올림 | 중앙값 사용(평균 아님) + MAD |
| **표본 부족 과신** | 1승 0패를 100%로 읽음 | Wilson 하한 |
| **귀속 오류** | 여러 규칙을 적용했는데 `because`가 하나 | 예측을 규칙별로 **분리 기록** |
| **지표 게이밍** | 저장률만 노려 콘텐츠가 이상해짐 | `direction: within` 하한 병기 |
| **자동 발행 유혹** | 루프가 돌면 발행도 자동화하고 싶어짐 | **§10 정책. 절대 금지** |

⚠️ **마지막 항목이 가장 위험하다.** 이 루프가 잘 돌수록 "발행만 자동화하면 완전자동"이라는 유혹이 커진다. 그런데 §10은 Threads 계정 보호 정책이고, 한 번 드리프트 재발로 재확인된 바 있다. **발행 승인은 영구히 사람이 한다.**
