# 케이스스터디 파이프라인 — 설계 판정

> **상태**: v1 확정 (2026-09-06). M0 구현 착수.
> **위치 판단**: 이 문서는 **제품 트랙**이다. `docs/*-design.md` 컨벤션을 따랐다
> (`review-collection-design.md`, `collection-architecture-design.md`와 같은 층).
> 방법론 트랙(`methodology/content/`)에 두지 않은 이유: 그쪽은 MANIFEST md5 대조와
> content-gate 스킬 `references/` 동기화가 매 커밋 걸리는 **정본 아카이브**다.
> 제품 스키마 설계서를 넣으면 30파일 매니페스트와 스킬 복사본이 오염된다.
> 이 파이프라인이 방법론 아카이브를 **쓰는** 것이지, 그 일부가 되는 게 아니다.

## 0. 무엇을 만드는가

브랜드·사업·SaaS 사례를 대량으로 조사해 케이스스터디로 적립하고, 그 데이터를 두 갈래로 쓴다.

```
                        ┌─ [A] PMF 진단 · 아이디어 제안
[리서치] → [검수] → [적립]┤
                        └─ [B] Threads 콘텐츠화 (기존 content-gate 통과)
```

기존 소구점 발굴 로직(VOC → `opportunity_score`)과 **다른 축**이다. 저쪽은
"이 시장에서 무엇이 안 채워졌나"(수요), 이쪽은 "그걸 채우는 방법이 남의 데서
실제로 통했나"(선례). 둘을 하나의 숫자로 합치지 않는다 — §2-2 참조.

## 1. v0 초안을 갈아엎은 지점

v0는 `case_studies` 한 테이블에 `what_worked[] / what_failed[]` 텍스트 배열을 두는
구조였다. 이걸 버렸다. **텍스트 배열로는 이 파이프라인의 두 목적을 둘 다 못 한다.**

- 배열 원소끼리 비교·집계가 안 된다. "타 브랜드에서 통했던 패턴을 참고"하려면
  원소 단위로 검색·매칭·집계가 돼야 하는데, `text[]` 는 그게 안 된다.
- 근거를 붙일 자리가 없다. `case_study_evidence` 를 케이스 단위로 분리해 놨지만,
  근거가 필요한 건 케이스가 아니라 **개별 주장**이다. "쿠팡 이탈했다"와
  "이탈 후 재구매율 2배"는 다른 근거를 요구한다.
- 수치·시점이 문장 안에 녹아 버려서 나중에 못 꺼낸다.

**대안: 케이스를 쪼갠다.**

| 층 | 단위 | 무엇인가 |
|---|---|---|
| `case_studies` | 브랜드/사업 1개 | 맥락. "누가, 어떤 시장에서, 어떤 상태였나" |
| `case_moves` | **무브 1개** | 실행 1개. "무엇을 바꿔서 무슨 수치가 어떻게 됐나" |
| `case_evidence` | 근거 1줄 | 그 주장을 뒷받침하는 출처 1개 |

**무브(move)** 가 이 시스템의 진짜 원자다. 매칭도 무브 단위, 승인도 무브 단위,
콘텐츠화도 무브 단위다. 케이스는 무브를 담는 맥락일 뿐이다.

그리고 여기서 방법론 아카이브의 장치를 그대로 빌려온다: **같은 무브가 서로 다른
케이스에서 3번 나오면 패턴으로 승격**한다(`case_patterns`, M1). 콘텐츠 판정의
"반복 3회면 승격"과 INF-06의 Wilson 하한 규칙이 같은 발상이다 —
한 브랜드에서 통한 건 일화, 셋에서 통하면 패턴.

## 2. 설계 질문 (초안 4개 + 2026-09-06 확정 2개)

### 2-1. (a) 매칭 — 태그 vs 임베딩 vs 하이브리드

**선택: 하이브리드. 단 우선순위는 `구조 패싯(하드 필터) → 임베딩(재순위) → LLM(근거 서술)`.**

| 안 | 문제 |
|---|---|
| 태그 단독 | 어휘 통제가 안 되면 아무것도 안 맞고, 통제하면 표현력이 없다 |
| 임베딩 단독 | **매칭 축이 틀린다.** 아래가 핵심 이유 |
| 하이브리드(임베딩 우선) | 위와 같은 문제를 순서만 바꿔 물려받는다 |

**임베딩을 1순위로 두면 안 되는 이유.** 케이스 요약 문장의 임베딩 유사도는
사실상 **업종 어휘 유사도**다. 탈모샴푸 셀러에게 "다른 탈모샴푸 브랜드"를
돌려준다. 그런데 이 서비스가 실제로 팔아야 하는 값은 그 반대다 —
**"업종은 다른데 병목이 같은 사례"**. 리뷰 신뢰가 병목인 D2C 셀러에게 필요한
건 다른 샴푸 브랜드가 아니라, 신뢰 병목을 깬 SaaS의 온보딩 무브일 수 있다.
업종으로 좁히는 건 이 제품의 차별점을 스스로 지우는 것이다.

그래서 **하드 필터는 병목(bottleneck)과 구매 구조**로 건다. 어휘 통제를 위해
패싯은 자유 태그가 아니라 **CHECK 로 고정된 5개 컬럼**이다(§3-2).
자유 서술은 `tags text[]` 로 따로 받되 매칭에 쓰지 않는다 — 사람 눈요기다.

**임베딩은 2순위 재순위로만.** 같은 병목 안에서 20건이 걸리면 그중 어느 게
더 비슷한 상황인지를 가리는 데 쓴다. 그리고:

> ⚠️ **pgvector 가용성은 현재 `확인 불가`다.** 이 프로젝트 마이그레이션·코드
> 어디에도 `vector`/`embedding` 이 없고(실측), 확장 목록은 이 세션에서 조회할
> 수단이 없다(MCP 가 다른 프로젝트에 잠겨 있음). **"없다"가 아니라 "못 봤다"다**
> (CLAUDE.md §7.1). M2 착수 시 `select * from pg_extension` 으로 먼저 확인한다.
> 없으면 임베딩 층은 통째로 빠지고, 패싯 + LLM 재순위만으로 돈다 — 그래도
> 파이프라인은 성립한다. 임베딩에 의존하지 않게 설계한 이유가 이것이다.

**매칭 0건의 3상태 (§7.1).** `pmf_assessments.match_status` 로 저장한다.

- `matched` — 조건에 맞는 무브를 찾았다
- `no_match` — **돌렸는데 없다**(양성 검사 후 음성)
- `not_run` — 매칭을 시도하지 않았다 (임베딩 미생성, 패싯 미입력 등)

`no_match` 와 `not_run` 을 같은 "0건"으로 찍지 않는다. 화면에 둘 다 "유사 사례
0건"으로 나오면 아무도 파이프라인이 멈춘 걸 모른다.

### 2-2. (b) `opportunity_score` 와의 합성

**선택: 합성하지 않는다. 독립 2축 + 사분면.**

| 안 | 왜 버렸나 |
|---|---|
| 가산 `O_k + 선례점수` | 단위·스케일이 다르다. 선례가 많다는 이유만으로 수요 없는 속성이 위로 올라온다 |
| 곱연산 `O_k × 선례계수` | 선례 0인 진짜 미개척 기회가 0으로 소멸한다. 가장 값진 칸을 지운다 |
| 상한/보정치로만 사용 | 실질적으로 곱연산의 열화판. "왜 깎였는지"가 안 남는다 |
| **독립 2축 (선택)** | 아래 |

두 값은 **애초에 단위가 다르다.** `opportunity_score = I + max(I−S, 0)` 는
**속성(aspect) 단위**의 수요 지표다. 케이스 근거는 **무브 단위**의 공급 지표다.
행이 1:1로 대응하지 않는다 — 하나로 합치려면 어느 쪽이든 뭉개야 한다.

그리고 합치면 **왜 높은지를 잃는다**. 이 둘은 액션이 정반대다:

```
                    선례 강함 ────────────→
      수요        │ ② 검증된 길        │ ① 레드오션
      (O_k)       │   실행 우선순위 1위 │   차별화 없이 들어가면 진다
      높음        ├────────────────────┼──────────────────────
        ↑         │ ③ 미개척           │ ④ 무시
        │         │   기회 크고 리스크 │   건드리지 않는다
                  │   크다. 실험 설계   │
```

②와 ③이 합산하면 같은 숫자가 되는데, 하나는 "따라 하면 된다"이고 다른 하나는
"아무도 안 해봤다"다. 절대 같은 칸에 두면 안 된다.

**제약과도 맞물린다.** `opportunity_score` 는 `GENERATED ALWAYS AS ... STORED`
컬럼이라 앱에서 못 건드린다. 2축 설계는 **건드릴 필요 자체가 없다.**
`pmf_assessments` 는 그 값을 **읽기만** 하고, 선례 축은 자기 컬럼에 따로 쓴다.

**단일 점수를 요구받을 때.** 정렬·목록 표시용 스칼라가 필요하면
`pmf_rank_key`(사분면 우선순위 → 축 값 순)를 **정렬 키로만** 노출한다.
헤드라인 출력은 사분면 라벨과 두 축 값이다. 한 숫자로 접어서 보여주면 그
숫자가 곧 "PMF 점수"로 읽히고, 근거가 지워진다.

### 2-3. (c) 리서치 신뢰성

**신뢰도는 케이스의 속성이 아니라 주장(무브)의 속성이다.** 그래서 등급은
`case_moves.evidence_grade` 에 붙고, `case_evidence` 행들로부터 계산한다.

`case_evidence` 가 갖는 축 **6개** — 하나로 뭉치면 안 되는 것들이다:

| 축 | 값 | 왜 별도 축인가 |
|---|---|---|
| `source_tier` | `primary` / `secondary` / `tertiary` | 1차(당사자 발표·IR·창업자 인터뷰) / 2차(기사·리서치) / 3차(요약 블로그·해설 영상) |
| `is_self_reported` | boolean | **tier 와 독립이다.** 창업자 인터뷰는 primary이면서 자기보고다 — 가장 흔하고 가장 위험한 조합 |
| `is_estimate` | boolean | **앞의 둘과 독립이다.** 비상장사 매출은 조사기관 추정치뿐인데, 앞의 두 축만 보면 "비자기보고 2차"라 최고 등급이 나온다. 아무도 실측한 적 없는 숫자다 |
| `is_regulatory_filing` | boolean | DART 감사보고서·SEC S-1/10-K/8-K. **자기보고이지만 허위기재에 법적 책임이 따른다** |
| `published_at` | date | **최신성은 `retrieved_at` 이 아니라 이것으로 판단한다.** 어제 긁어온 2019년 기사는 어제 정보가 아니다 |
| `retrieved_at` | timestamptz | 우리가 언제 봤나. 원문이 사라졌을 때 대조용 |

> **뒤의 두 축은 시범 5건(M0)을 돌리고 나서 추가했다.** 초안은 앞의 4축이었다.
> 실제로 조사해 보니 두 군데서 등급이 뒤집혔다:
> - Liquid Death 매출은 전부 Sacra **추정치**인데 "비자기보고 2차 2곳"이라 A 가 나왔다.
> - Casper S-1 과 Duolingo 8-K 는 **법정 공시**인데 "자기보고 1차뿐"이라 C 로 떨어졌다.
>   같은 표에서 출처를 안 밝힌 블로그 2개는 A 였다.
>
> 산식이 보수적인 게 아니라 **틀린** 것이었다. 표본 5건에서 두 번 나온
> 역전이라 우연으로 두지 않았다. 마이그레이션이 아직 미적용이라 컬럼을
> 추가하는 쪽이 나중에 ALTER 하는 것보다 싸다는 판단도 있었다.

**등급 산식** (파이프라인이 계산해서 쓴다):

- **A** — 법정 공시 1개. 또는 비자기보고·비추정 primary 1개. 또는 서로 독립인 실측 출처 2개 이상
- **B** — 자기보고 primary 1개 + 다른 도메인의 비추정 1·2차 출처 1개
- **C** — 교차 확인이 없다 (단일 출처 / 추정치뿐 / 3차뿐)
- **D** — 수치가 없다 (서술만 있다)

"독립"은 도메인이 다른 것으로 센다. 같은 보도자료를 받아쓴 기사 5개는 1개다.
3차 출처와 추정치는 **뒷받침에 세지 않는다** — 원 수치를 옮겨 적은 것이거나
아무도 재지 않은 값이라, 독립적인 확인이 아니다.

**D 등급을 버리지 않는다.** 저장은 하되 PMF 스코어링 입력에서 제외한다.
"근거가 약함"과 "존재하지 않음"은 다르고, 방법론 아카이브가 상충 진술을
버리지 않고 판정선을 붙인 것과 같은 원칙이다.

**수치 주장은 근거 없이 저장 금지.** `metric_after` 가 채워졌는데
`case_evidence` 행이 0개면 파이프라인이 거부한다. LLM 환각이 수치로 들어오는
경로가 여기 하나뿐이라 여기만 막으면 된다.

### 2-4. (d) 실명 · 저작권 · 사실관계

**선택: 실명 유지 + 인용 최소 + 출처 명시. 익명화하지 않는다.**

익명화("어떤 D2C 브랜드가")를 버린 이유는 법적 판단이 아니라 **방법론과 충돌**하기
때문이다. 공통 관문 U-3(관찰)과 프드프 G-9(하방선)은 구체 고유명사와 실물
관찰을 요구한다. 익명화하면 독자가 검증할 수 없고, 게이트를 통과할 수도 없다.
검증 불가능한 성공담은 이 아카이브가 제일 싫어하는 형태다.

실제 리스크는 실명이 아니라 셋이다: **(1) 인용 분량 (2) 사실 아닌 단정
(3) 부정적 평가.** 각각에 장치를 건다.

- **(1) 인용 분량** — `case_evidence.snippet` 는 **300자 상한**. 원문 전문 저장
  금지. 발행 콘텐츠에는 스니펫을 그대로 싣지 않는다. 수치와 출처만 인용하고
  서술은 자기 문장으로 쓴다.
- **(2) 사실 아닌 단정** — 발행 전 **사실 정합성 검사**를 통과해야 한다.
  본문의 수치·시점·브랜드명이 `case_moves` / `case_evidence` 행과 일치하는지
  대조한다. ★ 이건 **게이트가 아니다.** 새 게이트를 만들지 않는다는 원칙대로,
  content-gate 는 그대로 두고 이건 데이터 정합성 검사로 파이프라인에 둔다.
- **(3) 부정적 평가** — `what_failed` 성격의 무브(`outcome_direction='negative'`)는
  **등급 A 만 발행 가능**. B 이하는 사내 참고용으로 잠근다. 명예훼손 리스크는
  전부 실패 서사에 몰려 있다.

**자동 발행은 여전히 절대 금지** (CLAUDE.md §10). 케이스 기반 콘텐츠도 예외가
아니다. 경로는 `content-gate 통과 → 남헌 검수 → 사람이 발행`. 이 파이프라인은
발행 API 를 호출하는 코드를 갖지 않는다.

### 2-5. (e) 웹서치 주체 — **확정: 에이전트가 직접 한다** (2026-09-06, L-44)

**결정: 검색 API 를 붙이지 않는다. 리서치는 에이전트(Claude Code)가 웹서치로
직접 수행하고, 스크립트는 지시문·검증·등급·저장만 맡는다.** 남헌 확정.

M0 에서 이미 그렇게 갈라 두었고, 이번에 그것을 **잠정 조치가 아니라 설계**로
확정한다. 이유는 리포에 코드 경로가 없다는 것만이 아니다.

- **"0건"의 뜻이 흐려지지 않는다.** 웹서치 래퍼를 두면 "결과 0건"이 *검색기가
  안 돌았다*인지 *진짜 없다*인지 구분 안 되는 층이 하나 더 생긴다(§7.1).
  에이전트가 직접 찾으면 못 찾은 것을 못 찾았다고 적을 수 있다.
- **판단이 검색 안에 있다.** 이번 라운드에서 값이 있었던 판단은 전부 검색
  결과를 고르는 단계에서 나왔다 — 듀오링고를 3차 블로그 대신 8-K 로 다시
  찾은 것, `[카페24x기업 공식몰]` 태그를 보고 자기보고로 내린 것. 이건
  쿼리 자동화로 대체되지 않는다.
- **속도가 병목이 아니다.** 검수자가 1명이라 리서치를 자동화해도 승인이 막힌다.

**이 결정이 뒤집히는 조건**: 케이스 50건을 넘겨서 사람이 붙는 시간이 실제
병목이 됐을 때. 그때는 자동화가 아니라 **후보 URL 수집만** 자동화하고,
등급·자기보고 판정은 계속 에이전트가 한다.

### 2-6. (f) 교차판정 C-01~C-12 와의 관계 (2026-09-06 대조, L-46)

지난 라운드 5건을 `cross-decisions.md` 12항목 전부에 대조했다.

**결론: C-01~C-12 를 `case_moves` 에 직접 적용하지 않는다. 층위가 다르다.**

C-01~C-12 는 **콘텐츠(게시물)** 층위의 판정선인데 `case_moves` 는 **사업 실행**
층위다. 그대로 대입하면 거짓 충돌이 난다.

> **실제로 났다.** 조선미녀 move1(POSITIONING — '한국 선크림'이 아니라 쌀 추출물
> 데일리 톤업이라는 **하위 카테고리로 좁혔다**)은 C-01("넓혀라")과 정면으로
> 어긋나 보인다. 그런데 C-01 은 *"이 분야에 관심 없는 사람도 볼 이유가 있는가"*
> 라는 **표본** 질문이고, 조선미녀가 좁힌 건 **아마존 검색어**다. 아마존 검색은
> 이미 구매의도가 있는 표본이라 넓힐 이유가 없다.
>
> 같은 단어("좁힌다")가 두 층위에서 반대 뜻이다 — 사고 #4(게이트 P-10 vs 규칙
> P-10)와 **같은 형태**다. 이걸 게이트로 걸었으면 조선미녀 무브가 C-01 위반으로
> 반려됐을 것이다.

케이스 무브는 콘텐츠의 **소재**이지 콘텐츠가 아니다. C-xx 가 걸리는 지점은
M3 의 **발행 초안**이고, 거기서는 기존 content-gate 가 이미 그 일을 한다.
**새로 만들 것이 없다** — 원래 원칙("새 게이트를 만들지 않는다")대로다.

**그럼 C-xx 와 이 파이프라인은 어디서 만나는가 — 3곳:**

| C-xx | 접점 | 이번 라운드 조치 |
|---|---|---|
| **C-08** (관찰·분석, ★불변) | **이 파이프라인이 C-08 의 기계화다.** 솔파 *"저는 진짜 몇천 개 읽어요"* / 프드프 *"유일한 필수 습관은 분석"* 이 곧 이번 트랙의 전제(*"감은 축적된 조사에서 나온다"*)다. §14-1 이 "C-08 은 상시 습관이라 초안 단계 항목이 아님"이라 비워 둔 자리를 이게 채운다 | **정합 확인만.** 게이트로 만들지 않는다 |
| **C-01** (타깃 범위, ★불변) | M3 발행 초안에서 걸린다. *"Casper 의 재구매율 16%"* 는 D2C 종사자만 볼 문장이다 | 기존 content-gate 가 처리. **추가 없음** |
| **C-05** (레퍼런스 출처, 🔀조건부) | 솔파 *"다른 매체에서"* vs 프드프 *"내 분야 먼저"* 의 통합 원칙이 **매칭 1순위 축 = 병목**과 같은 구조다. 병목이 같은 *다른 업종* 사례를 먼저 내고 같은 업종은 보조로 붙이는 것이 곧 "다른 매체에서" 다 | **M1 에서 확인할 것.** C-05 조건표에 케이스 매칭 결과를 넣을 자리가 있다 |

**추가 관측 2건 (기록만, 이번 라운드에 `cross-decisions.md` 는 건드리지 않았다):**

- **C-09 (하방선 — 솔파 고유 / 프드프 결손)** — Casper 케이스가 정확히 하방선
  결손 사례다. `outcome_direction='negative'` 무브 2개가 *"이 전략을 어떤
  상품에서 쓰면 안 되는가"* 를 말한다. C-09 의 **전이 권장**을 뒷받침할 실증
  사례가 처음 생겼다.
- **⚠️ C-02 (감·재능 — 미해결 충돌)** — 이번 트랙의 전제는 **프드프 쪽 손을
  들어준다.** 솔파 R-12(*"평생을 노력해도 어릴 때부터 쌓아온 감을 이기기는
  어렵다"*)와 어긋난다. §14-3 은 미해결 충돌을 만나면 **판정 로그를 남기라**고
  하는데, 이번 라운드 지시가 `cross-decisions.md` 를 건드리지 말라는 것이라
  **쓰지 않았다.** M1 착수 시 판정 로그 1건으로 남길 것. 예측: 케이스 20건 이상
  적립 후 매칭이 실제로 쓸 만한 제안을 내면 프드프 쪽 조건이 강화된다.

**대조한 나머지 7건 (C-03·C-04·C-06·C-07·C-10·C-11·C-12)** — 5건 어디에도
걸리지 않았다. 전부 콘텐츠 제작 층위(초반 몇 초, 알고리즘, 연출 진위, 현실
연결, 효율화, 라벨 부여, 스토리텔링)라 사업 실행 무브와 접점이 없다.
**"확인해 보니 없다"이지 "안 봤다"가 아니다.**

## 4. v0 가 놓친 리스크

### 4-1. `approved` 가 "사실이다"로 읽힌다 ★

v0 의 `review_status(draft/approved/rejected)` 하나로는 **"남헌이 봤다"와
"근거가 충분하다"가 구분되지 않는다.** 승인된 D등급 케이스가 반드시 존재하는데
(맥락은 맞지만 수치 근거가 없는 사례), 단일 상태로는 그게 표현이 안 된다.
이 리포에서 검사 결과를 잘못 읽어 사고 난 게 여섯 번이다.

→ **검수 축(`review_status`)과 근거 축(`evidence_grade`)을 분리.** 소비하는 쪽은
둘 다 본다: PMF 스코어링은 `approved AND grade IN ('A','B')`, 콘텐츠화는
`approved AND (grade='A' OR outcome_direction<>'negative')`.

### 4-2. `valid_until` 은 아무도 못 채운다 ★

"시대에 안 맞을 위험"을 `valid_until` 로 잡자는 건 **미래를 예측하라는 요구**다.
채울 근거가 없으니 전부 NULL 로 남고, NULL 이 "유효기간 없음"으로 읽힌다.
이 리포에 이미 그 꼴인 컬럼이 있다 — `profile_clicks` 는 수집기가 한 번도
안 채워서 NULL 인데, 화면에서는 "프로필 클릭 0"과 구분되지 않았다.

→ **`observed_period_start/end` 를 필수로.** "언제 관측된 사실인가"는 과거형이라
리서치 시점에 실제로 채울 수 있다. 낡음 판정은 저장이 아니라 **조회 시점**에
나이를 계산해서 한다. 사실만 적고 판단은 읽을 때 한다.

### 4-3. 검수 병목이 파이프라인 전체를 막는다 ★

웹서치는 무한히 생성되고 승인자는 1명이다. 검수 큐 처리량이 곧 파이프라인
처리량인데, v0 에는 이걸 완화할 장치가 없다.

→ **승인 단위를 케이스가 아니라 무브로 쪼갠다.** 케이스 하나에 무브 5개면
3개만 승인하고 2개는 보류할 수 있다. 전부-아니면-전무 승인이 병목의 실제
원인이다. 케이스 승인은 "맥락이 맞다"만 뜻하고, 무브 승인이 실제 관문이다.

→ 그리고 **draft 를 숨기지 않는다.** M0 는 지시대로 파일 스테이징으로 시작하되
(§5 M0), 큐 길이와 대기 시간을 항상 출력한다. 병목을 안 보이게 하면 병목이
없어지는 게 아니라 측정이 없어진다.

### 4-4. 생존 편향 — 실패 사례는 구조적으로 안 잡힌다

웹서치는 "성공 사례"에 압도적으로 쏠린다. 망한 브랜드는 회고를 안 쓴다.
그대로 두면 `what_failed` 가 영원히 얇고, 그 얇음이 "실패가 드물다"로 읽힌다.

→ `outcome_status` 기본값을 **`unknown`** 으로 둔다(`active` 아님). 지금 살아
있는지 확인 안 했으면 확인 안 한 것이다. 실패 사례는 별도 수집 경로(폐업 공시·
피벗 회고·철수 발표)로 따로 돌린다 — M1.

### 4-5. 같은 브랜드 재조사가 중복 행을 만든다

두 번 조사하면 두 케이스가 생기고, 둘 중 뭐가 맞는지 아무도 모른다.

→ `slug` UNIQUE. 재조사는 **새 케이스가 아니라 기존 케이스에 무브·근거를
추가**한다. 방법론 아카이브의 append-only 와 같은 형태다.

### 4-6. robots / 인용 — "못 읽었다"를 "허용"으로 읽지 않는다

CLAUDE.md §7.1 의 5번 사례가 정확히 이거다. 케이스 리서치는 WebSearch 기반이라
기존 `review_sources` robots 계층을 타지 않는다.

→ 원문 전문을 저장하지 않고 300자 스니펫 + URL 만 남긴다. 크롤링이 아니라
검색 결과 인용이라 층위가 다르지만, **저장 분량을 구조적으로 못 늘리게** 막는
쪽이 정책 문서보다 확실하다.

### 4-7. `because:` 오염 (§3-4 참조)

## 7. 발행 게이트 `CG-` (2026-09-07 신설)

### 7-1. 왜 새 접두사인가 — `G-` 를 이어 쓰지 않는다

방법론 아카이브에는 이미 게이트 코드가 있다: `solfa/02-gate.md` 가 `G-0~G-10`,
`pdp/02-gate.md` 가 `G-0~G-13`. 여기에 `G-14` 를 이어 붙이는 건 하지 않는다.

- **두 폴더가 같은 `G-` 아래에서 다른 뜻으로 번호를 쓰고 있다.** 거기에 하나 더 얹으면
  "게이트 P-10 vs 규칙 P-10"(HANDOVER-LOG 사고 4)과 정확히 같은 모양이 된다.
- **층위가 다르다.** `G-` 는 남헌의 **글쓰기 방법론**이다. 이건 케이스 데이터의 **근거 강도**에
  관한 규칙이고, 판정 재료가 DB 컬럼(`case_moves.evidence_grade`)이다.
- **정본 위치가 다르다.** `methodology/content/` 아래 문서는 MANIFEST md5 로 출처가 묶여 있는
  아카이브다(사고 2·3 이 거기서 났다). 파이프라인 규칙을 그 안에 끼워 넣지 않는다.

그래서 **`CG-`(Case Gate)** 로 새로 채번한다. 정본은 이 문서이고, 구현은
`lib/cases/publish-gate.ts` 다. 기존 코드(`G-` `U-` `D-` `X-` `R-` `P-` `C-` `LOG-` `UPD-`)와
접두사가 겹치지 않는다 — `C-01`(cross-decisions)과 `CG-1` 은 `\bC-\d` 로 서로 안 걸린다.

`case-draft-stage.mjs` 가 500자 상한을 `G-11`(pdp)로 인용하는 건 그대로 둔다. 그건 실제로
글쓰기 규격 게이트이고, 이번에 새로 만든 것과 다른 규칙이다.

### 7-2. `CG-1` — 등급 C 무브를 인용하면 출처 귀속 문구를 요구한다

**결정(L-62).** 등급 C 무브는 발행 금지가 아니라 **조건부 발행**이다.
A·B 는 자유 발행. C 는 본문에 **출처 귀속 문구**가 없으면 `pending_review` 로 올라가지 않는다.

**왜 금지가 아닌가.** C 는 "근거가 없다"가 아니라 "제3자 확인이 없다"이다. 금지로 두면
케이스 13건이 통째로 죽는다. 대신 독자가 그 숫자의 출처를 알고 읽게 만든다 —
Nubank 20-F 가 스스로 "not independently verified"라고 적는 것과 같은 수위다.

**통과 조건.** 아래 중 하나가 본문에 있어야 한다.

- 자기 귀속 표지: `자사 발표/집계/기준`, `회사 발표/자료`, `회사가 밝힌/발표한`,
  `자체 집계/정의/기준`, `스스로 밝힌`, `공시 기준`, `제3자 검증 없음 명시`, `독립 검증 없음 명시`
- 이름 귀속: 브랜드명 + 25자 이내의 `밝혔다/발표했다/공개했다/공시했다/집계했다`

**통과시키지 않는 것.** `업계에 따르면` 처럼 주체를 흐리는 표현. 그건 귀속이 아니라 얼버무림이다.
일반적인 `~에 따르면` 을 패턴에 넣지 않은 이유가 이것이다.

**이 게이트가 확인하지 못하는 것 (§7.1).** 귀속 문구가 **본문에 있는가**만 본다.
그 문구가 **문제의 그 수치에 붙어 있는가**는 확인하지 못한다. 아무 데나 한 줄 넣어도 통과한다.
그래서 통과는 "사람이 안 봐도 된다"가 아니라 "사람이 볼 준비가 됐다"는 뜻이고,
통과 시에도 그 한계를 화면에 찍는다.

**막혔을 때의 동작.** 저장을 건너뛰지 않는다. `status='draft'` 로 눕히고 **exit 4** 로 구분한다.
본문을 날리면 사람이 고칠 대상 자체가 사라진다. 이미 `pending_review` 였던 글이 나중에
재채점으로 강등돼 막히는 경우도 여기로 오고, 그때는 **끌어내리는 게 맞다**(L-63 재발 방지).

**어떤 API 도 부르지 않는다.** 순수 로컬 텍스트 검사다. 이 게이트는 발행 가능/불가를
판정만 하고, 실제 게시는 여전히 사람이 Threads 앱에서 직접 한다 (CLAUDE.md §10).

**검증.** `case-pipeline-selftest.mjs` 에 12건(74/74 중). 게이트를 일부러 망가뜨리면
그중 6건이 실제로 실패하는 것까지 확인했다 — 통과할 수만 있는 검사가 아니다.

### 7-3. 알려진 한계 — 게이트는 "붙어 있는가"를 못 본다 (L-64 와 같은 뿌리)

`CG-1` 이 확인하는 것은 **귀속 문구가 본문 어딘가에 있는가** 뿐이다. 그 문구가 문제의
그 수치 옆에 붙어 있는지는 못 본다. 문구를 맨 아래 한 줄 넣어도 통과한다.

같은 어긋남이 등급 산식에도 있다. `gradeMove` 는 근거를 **무브 단위**로 세는데, 근거는
실제로 **주장 단위**로 붙는다. 9차 RETENTION 재조사에서 실물이 나왔다 —
`chewy-autoship-retention/PRODUCT_FEATURE` 는 (a) Connect with a Vet 이 Autoship 전용
혜택이었다 (b) 고객당 순매출 434→555 달러, 두 주장을 함께 담는다. 여기에 (a) 만 다루는
독립 매체 행을 하나 넣으면 **(b) 는 아무도 교차 확인하지 않았는데 등급이 C→B 로 오른다.**

그래서 그 행을 넣지 않았고, `L-64` 로 등재했다. 해법은 근거를 "무브"가 아니라
"무브 안의 어느 주장"에 매다는 키다 — `L-60`(원 관측 키)과 같이 설계한다. 그때까지
**등급 B 이상이라도 그 B 를 만든 근거가 어느 문장을 받쳐 주는지는 사람이 확인해야 한다.**

## 8. 원 관측 키와 수치 뒷받침 — `L-60` + `L-64` 해소 설계 (2026-09-07, 10차)

### 8-1. 두 결함은 한 문장으로 합쳐진다

- `L-60` — 독립성을 **도메인**으로 셌다. 한 공시를 옮겨 적은 뉴스레터 두 곳은
  도메인 2개라 "독립 근거 2건"이 되고 등급이 A 로 올랐다. 도메인은 2개지만 **관측은 1개**다.
- `L-64` — 근거를 **무브** 단위로 셌다. 무브가 두 주장을 담을 때 앞쪽만 받치는 근거가
  뒤쪽 수치의 등급까지 올렸다(§7-3).

**산식이 세는 단위는 "행"인데, 세야 하는 것은 "서로 다른 관측 × 그 관측이 실제로
받치는 주장"이다.** 그래서 축을 두 개 더한다. 마이그 `20260907000001`.

| 컬럼 | 뜻 | NULL 의 의미 |
|---|---|---|
| `observation_key text` | 이 행이 전하는 **원 관측**의 이름. 같은 관측을 옮긴 행끼리 같은 값 | 확인하지 않았다 |
| `supports_metric boolean` | 이 행이 무브의 **수치**를 직접 받치는가 (서사만 받치면 false) | 확인하지 않았다 |

키 규약: `<발행주체>-<문서종류>-<기간>`, 소문자·하이픈
(`chwy-10k-fy2023` / `duol-8k-2023q2` / `sensortower-panel-2023q3`).
CHECK `^[a-z0-9]+(-[a-z0-9]+)*$` 로 모양을 강제한다 — 빈 문자열도 막는다.
빈 문자열은 NULL 과 다른 값이라 "키를 적었다"로 세어지기 때문이다.

판정 질문 한 문장: **"이 행이 사라지면 우리가 잃는 관측이 무엇인가."**
다른 행과 같은 것을 잃으면 같은 키다. 9차에 확보한 Retail Dive 기사가 정확히 그 예다 —
본문이 "according to newly minted CFO David Reeder" 라고 귀속한다. 사라져도 10-K 가
남으면 잃는 게 없다. **독립 도메인이지 독립 관측이 아니다.**

### 8-2. 산식 — 어디에 적용하고 어디에 적용하지 않는가

`gradeMove` 의 경로를 둘로 나눈다. **문서의 성격을 보는 경로**와 **개수를 세는 경로**다.

- **문서 성격 경로** (`attested`: 법정 공시 / `nonSelfPrimary`: 비자기보고 1차) — 키를 요구하지 않는다.
  여기서 A 가 나오는 근거는 "여럿이 말했다"가 아니라 "이 문서가 법적 책임 아래 말했다"라서,
  관측이 하나뿐이어도 성립한다. 다만 `supports_metric === false` 로 **명시된** 행은 제외한다.
- **개수 세는 경로** (교차 확인) — `supports_metric === true` 이고 `observation_key` 가 있는 행만
  센다. `foldObservations` 로 키를 접은 뒤 **키 가짓수 ≥ 2** 여야 A 다.
- 자기보고 1차 + 다른 관측 → B. 여기서 "다른"은 자기보고 행의 키와 **다른 키**를 뜻한다.
  같은 키뿐이면 C 다. 이게 `L-60` 의 핵심 수정이다.

세지 않은 행이 있으면 이유를 등급 사유에 남긴다 —
`(교차 확인 후보 3건 중 3건은 관측 키·수치 뒷받침 미기재라 세지 않았다)`.

### 8-3. 이 설계의 가장 큰 위험 — 하락을 "근거가 약해졌다"로 읽는 것

두 축 다 NULL 을 허용하고 산식은 NULL 을 세지 않는다. 그래서 **적용 직후 등급이 내려간다.**
백필 전 실측 투영(`regrade --dry --force`, 32 무브):

```
이전 A13 · B5 · C13 · D1
이후 A12 · B0 · C19 · D1     (바뀐 것 6개, 그중 잠정 15개)
```

**이 하락은 근거가 나빠져서가 아니라 아직 안 적어서다.** `L-56` 때와 같은 함정이고,
결과만 보면 둘이 구분되지 않는다. 그래서 코드에 세 겹을 박았다.

1. `GradeResult.provisional` — "관측 키 미기재라 판정 못 함"으로 내려간 등급에 표시가 붙는다.
   `regrade` 가 끝에 `그중 N개는 **잠정**이다` 를 찍는다.
2. `regrade` 커버리지 가드 — 컬럼이 없거나(42703) 키가 **한 행도 없으면** 계산하지 않고
   exit 2 로 멈춘다. `--force` 로만 넘어간다.
3. `--force` 는 `--dry` 와만 쓴다 — 백필 전 투영을 DB 에 쓰면 "안 적었다"가 "약하다"로 굳는다.

### 8-4. 버린 안

- **`claim_key` 자유 텍스트로 주장을 식별** — 표기가 사람마다 흔들려서(`매출`/`순매출`/`revenue`)
  같은 주장이 다른 키가 된다. 축이 있는데 검증이 안 되는 상태가 축이 없는 것보다 나쁘다(§7.1의 같은 논리).
  대신 `supports_metric` 하나로 "무브의 `metric_name` 을 받치는가"만 묻는다 — 무브당 수치는 하나뿐이라
  이걸로 `L-64` 는 닫힌다. 주장이 3개 이상인 무브는 **무브를 쪼개는 게 맞다.**
- **`supports_metric NOT NULL DEFAULT true`** — 기존 72행이 전부 "수치를 받친다"로 접힌다.
  확인하지 않은 것이 확인된 것으로 둔갑한다. 하락을 피하려고 NULL 상태를 지우는 셈이라 §7.1 위반이다.
- **도메인 카운트를 유지하고 예외 목록을 두는 것** — 예외는 사람이 관리해야 하고,
  "이 매체는 복창한다"는 매체 속성이 아니라 **기사별 속성**이다. Retail Dive 도 자체 취재를 한다.

### 8-5. 남는 한계

- **키를 짓는 사람이 틀리면 산식도 틀린다.** CHECK 는 모양만 본다. 서로 다른 관측에 같은 키를
  붙이면 A 가 C 로, 같은 관측에 다른 키를 붙이면 C 가 A 로 간다. 후자가 위험하다.
- 그래서 백필은 스크립트가 아니라 **사람이 본문을 읽고** 한다. `20260907000001` 파일의 (4) 지침에
  9차까지 원문으로 확인한 행만 적어 뒀다. **모르는 행은 NULL 로 둔다.**
- `CG-1` 의 한계(§7-3 앞 문단)는 그대로 남는다. 귀속 문구가 그 수치 옆에 붙었는지는 여전히 못 본다.
