## 1. 무엇을 바꿨나

원인(S0 Q5): ① 3페이지 상한에서 러너가 커서를 버린다(`resetAtCap`) → 121번째 이후 옛 리뷰는 어떤 실행도 못 읽는다. ② 새 글 0건 3회면 닫는다(`emptyClose`) → 리뷰가 적은 앱은 금방 exhausted, 그것도 빈 커서라 "진짜 끝"인지 "못 내려감"인지 못 가른다.

타깃 하나의 흐름:
1. 첫 방문(커서 없음): 3장 읽고 상한 → 커서 `{"b":"<4장째 토큰>"}` 보관(예전엔 버림).
2. 다음 방문: 최신 1장 → 이미 본 구간 → 남은 2장 몫으로 `b` 부터 옛 쪽. 상한이면 다음 `b` 보관, 목록 끝이면 `{"end":1}`.
3. `b` 가 남아 있는 동안은 새 글 0건이어도 닫지 않는다. `end` 표시 뒤에는 예전 규칙(0건 3회 → exhausted)대로 닫힌다 = **진짜 고갈 표시가 붙은 exhausted**.
4. 이미 exhausted 인 ≤50건 타깃(빈 커서): 다시 보기로 골라져 최신부터 끝까지 내려간다(이미 본 리뷰는 지문이 거른다). 새 글이 나오거나 옛 쪽이 남으면 active, 아니면 끝 표시와 함께 다시 exhausted.

요청 수: 러너 예산(`min(daily_request_cap, 램프 목표) − 오늘 쓴 요청`, 실행 몫)·간격·robots 소유자 예외 판정·403/429/빈 응답/캡차 즉시 중단은 **한 줄도 안 바꿨다**. 깊이 페이지도 같은 예산을 쓴다(셀프테스트: 상한 2 → 요청 2회, 옛 쪽 429 → 그 자리에서 중단).

## 3. 첫 실행 뒤 확인(읽기 전용 SQL)

```sql
select
  count(*) filter (where status='exhausted')                                  as exhausted,
  count(*) filter (where status='exhausted' and cursor is null)               as exhausted_empty_cursor,
  count(*) filter (where status='exhausted' and total_collected <= 50)        as gp_le50_exhausted,   -- 기준 74 (처음 91)
  count(*) filter (where status='exhausted' and cursor like '%"end":1%')      as exhausted_end_marked, -- 0 에서 늘어야 한다
  count(*) filter (where cursor like '%"b":"%')                               as deep_pending,
  round(avg(total_collected) filter (where status='exhausted'), 1)            as avg_exhausted          -- 기준 55
from review_targets where source_key = 'googleplay';
```

- 수집 로그(perTarget 문구)에서 `옛 쪽 커서는 보관` 과 `이번 실행 몫 종료` 가 보여야 한다.
- 구글 플레이 실행의 `requests` 합이 하루 상한·램프 목표를 넘지 않는지(`review_collection_runs`).
- **판정 주의(§7.2)**: `exhausted_end_marked` 가 늘었는데 그 타깃들의 `total_collected` 가 그대로면 아래 위험 1을 의심한다.

## 4. 위험

1. **토큰 수명을 실측하지 않았다(가장 큰 위험).** 하루 넘게 보관한 `b` 토큰을 Play 가 받아 줄지 모른다. 거부가 파싱 실패로 오면 상태를 버리고 다음 방문이 최신부터 다시 내려간다(요청만 더 든다). **빈 목록으로 오면 끝으로 오판해 `end` 를 붙인다** — 위 SQL 의 주의 항목으로 잡는다. 확인되면 back 페이지의 빈 응답은 끝 표시 대신 상태 초기화로 바꾼다.
2. 넓이 ↔ 깊이: 타깃당 요청이 1회 → 최대 3회로 늘어 하루 40 안에서 방문 타깃 수가 준다. 다시 보기가 방문 active 앞에 서므로 실행당 최대 5 × 3 = 15 요청을 먼저 쓴다. 줄이려면 `GP_REVISIT_PER_RUN` 을 낮춘다.
3. §10.1 경계 확인 요청: exhausted → active 되살리기는 지금까지 `scripts/target-revive.mjs` 만 했다. 이 PR 은 선택만 넓히고, 쓰기는 러너의 기존 진행 저장(`status`·`cursor`·`consecutive_empty`·`total_collected`·`last_run_at`)으로 한다 — 새 글이나 남은 옛 쪽이 있을 때만 active 로 남는다. 리뷰어가 이 경로를 허용 범위로 보는지 판단해 달라.
4. 약관·robots: 새 경로·새 헤더 없음. 같은 batchexecute 경로, 같은 소유자 예외(`owner_2026-10-06`), 우회 없음.
5. `oldestAt`(지시 제안)는 넣지 않았다 — 어댑터가 이미 페이지 안 날짜로 "이미 본 구간"을 판정해 쓸 곳이 없다.
