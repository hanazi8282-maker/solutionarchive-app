- 상태
  - 코드: 머지 전 PR

## 0. 먼저 — 지시와 실물이 다른 것 1개

- **"case_studies/case_moves 에 review_status='approved' 를 기록하는 경로"는 만들지 않았다. 만들 수 없는 구조다.**
- 1차·2차 판정은 `input_id`(리뷰 1건) 단위다. `case_studies`·`case_moves`·`case_evidence` 에는 input_id 로 이어지는 컬럼이 없다(마이그레이션 전체를 grep 해서 확인했다).
  - 케이스는 브랜드 조사에서 나온다. 리뷰에서 나오지 않는다.
  - "두 판정이 동의한 리뷰 → 어느 케이스를 승인할지"를 정할 자리가 데이터에 없다.
- §10.1 조건 5도 이 예외를 "관련성 자동 승인 하나"로 묶었다. `case_moves` 별도 승인 버튼은 사람 몫으로 남겨 두었다. 09-27 설계 §2-3 결정 1 권고 A와 09-28 cowork 보고 §3-2 Q1 도 같은 결론이다.
- 그래서 승인은 **판정 행 자신**(`review_relevance_verdicts.auto_approved_at`)에 기록한다.
  - 승인의 효과: 그 행은 사람 "신규 채점" 줄에서 빠지고, 감사 표본 모집단으로 들어간다.
  - extract 입력과 `/signals` 공개는 지금도 1차 relevant 하나로 이미 일어나는 일이라 바뀌지 않는다(09-27 설계 §3-3).
- 케이스 승인까지 자동화하려면 케이스와 리뷰를 잇는 신호를 따로 설계해야 한다. **남헌 결정 1**(아래 §7).
- CLAUDE.md §10.1 예외 문단의 "무인 루프가 review_status='approved' 를 직접 기록" 문구는 이 문서의 구현과 어긋난다. 문단이 구현 세부를 이 문서에 위임했으니 이 문서가 정본이다. 그래도 문구 정정은 남헌 또는 역할 세션 몫이다. CLAUDE.md 2차 편집은 분류기가 막는다.

## 1. 구현 — 어디에 무엇이 있나

- 판정 함수: `lib/analysis/auto-approval.ts` `isFullAgreement(row, since)`. 아래 네 가지가 모두 맞을 때만 true 다.
  - `verdict === 'relevant' && second_verdict === 'relevant'`
  - `human_verdict IS NULL`
  - `auto_approved_at IS NULL`
  - `judged_at ≥ since`
  - 판정이 하나뿐이거나 unknown·irrelevant 가 하나라도 섞이면 false 다(조건 1).
- 게이트: 같은 파일 `autoApprovalGate`. 플래그 → 시행일 → 감사 조회 → 킬스위치 순서로 보고, 하나라도 막히면 닫힌다. **기계는 끄기만 하고 켜지 못한다.**
- 집행: `scripts/relevance-auto-approve.mjs`
  - `nightly-relevance.yml` 의 판정 뒤 스텝에서 돈다. `continue-on-error` 라 야간 판정을 깨지 않는다.
  - 플래그가 꺼져 있으면 DB 도 열지 않고 exit 0.
  - UPDATE 의 WHERE 에 조건을 다시 건다. 그사이 사람이 채점한 행은 덮지 않는다.
  - verdict·human_verdict·라벨·케이스 테이블은 쓰지 않는다(셀프테스트로 고정).
- 2차 판정의 DB 경로: `scripts/relevance-second-opinion-import.mjs --record-second`
  - 확인 결과, 지금의 `--apply` 는 라벨 4개만 채운다(`update({impact, frequency, community_signal, wtp_mentioned})`). verdict 도 승인도 건드리지 않는다.
  - 새 플래그는 `second_verdict / second_model / second_judged_at` 만 쓴다.
  - **파일의 `criteria_version` 이 현재 기준과 다르면 통째로 거부한다.** 09-27·09-28 결과 파일은 버전이 없어서 기록되지 않는다(조건 2).
- 스키마: `supabase/migrations/20260930000027_relevance_auto_approval.sql` + 롤백.
  - nullable 컬럼 5개: second_verdict, second_model, second_judged_at, auto_approved_at, auto_approval_rule
  - 부분 인덱스 1개
  - **미적용.** 비파괴이고 §10.2 예외 5개에 걸리지 않아 역할 세션이 자체 판단으로 적용할 수 있다.
- 셀프테스트: `scripts/auto-approval-selftest.mjs`(41건). `build-check.yml` 에 넣었다.

### 켜는 법 (오케스트레이터·남헌 — 지금은 켜지 않는다)

1. 재시험 90% 이상을 확인한다(`reports/2026-09-28/t2-criteria-retest.md`).
2. 마이그레이션 000027 을 적용한다.
3. 기준 통일 PR 을 머지한다. 머지한 날짜(KST)가 시행일이다.
4. 새 export(`criteria_version` 포함) → 2차 판정 → `import --record-second` 순으로 2차 판정을 DB 에 넣는다.
5. 리포 변수를 넣는다: `AUTO_APPROVAL_SINCE=<시행일>`, `AUTO_APPROVAL_ENABLED=true`.
   - 시행일 이전에 판정된 1차 행은 옛 기준이라 대상이 아니다. 재판정은 새 입력부터 자연히 쌓인다.

### 알려진 한계

- **2차 판정은 아직 야간 자동이 아니다.** 지금은 클라우드 세션이 파일을 만들고 사람이 import 한다. 그래서 자동 승인의 양은 2차 판정을 돌린 만큼만 생긴다.
- 2차 판정자 모델(Gemini 유지, 구독 업그레이드 조사 중)은 다른 세션 몫이라 건드리지 않았다.

## 2. 감사 표본 — 하루 5건

### 규모와 이유

- **하루 5건**(`AUDIT_DAILY = 5`, `--audit` 로 조정).
- 킬스위치가 판정하려면 감사 창 **50건**이 필요하다(§3). 5건/일이면 평일 2주에 창이 찬다.
- 사람 채점 트랙 15건/일에 더하면 하루 20건이다. 행 1건은 원문 400자 안팎이라 추가 부담은 몇 분 수준이다[추정 — 처리 시간은 아직 재지 않았다].
- 10건/일이면 창이 1주에 차지만, 사람 몫이 하루 25건으로 늘어난다. 창을 빨리 채울수록 킬스위치는 빨라지지만 정확도 문턱은 같다. 첫 2주는 워밍업이라(§3) 5건으로 충분하다.
- 유입량 대비 비율로 정하지 않았다.
  - 비율로 정하면 유입이 늘 때 사람 몫도 따라 는다. 그러면 사람이 대충 넘기게 된다(정답 오염).
  - 킬스위치에 필요한 것은 비율이 아니라 **창 크기**다.

### 사람 채점 트랙과 한 화면·한 테이블

- **새 UI·새 테이블을 만들지 않았다.** 확인해 보니 관련성 판정의 사람 채점 UI 는 앱에 없다.
  - `app/` 에서 `human_verdict` 를 쓰는 곳은 0곳이다. `/signals` 는 읽기만 한다.
  - 기존 워크플로는 마크다운 채점표다. `scripts/relevance-grading-sample.mjs` → 사람이 체크 → `scripts/relevance-grading-import.mjs` → `human_verdict`·`human_graded_at` 순서로 간다.
  - `/cases/grade` 는 케이스 카드 승인이다. 다른 줄이다.
- 그 채점표를 넓혔다.
  - `relevance-grading-sample.mjs --n 15 --audit 5` 로 **신규 채점 15장 + 감사 5장이 한 표**에 나온다.
  - 신규 채점은 자동 승인되지 않은 행에서만 뽑는다. 사람 시간은 기계가 못 정한 쪽에 쓴다.
  - 감사 5장은 자동 승인 행에서 무작위로 뽑는다(seed 재현).
  - 두 묶음을 uuid 순으로 섞는다. 표에 어느 줄이 감사인지 **표시하지 않는다**(09-27 설계 위험 6 — 채점자가 알면 끌린다).
  - 칸은 `관련 / 무관 / 모름` 3개다. `모름`을 새로 넣었다.
    - "읽었는데 판단 불가"(`human_verdict='unknown'`)와 "안 봄"(빈칸)이 갈린다.
    - 옛 두 칸 표도 그대로 읽는다(셀프테스트).
- 기록은 같은 `human_verdict` 다. 감사 결과는 **"자동 승인된 행 ∧ 사람 채점 있음"**으로 집계한다. 표시 컬럼을 따로 두지 않는다.
  - 사람 채점 트랙이 우연히 자동 승인 행을 채점해도 유효한 감사 1건이다. 선택이 정답에 기대지 않기 때문이다.
- 감사 채점은 이미 있는 경로로 1차 판정의 few-shot 에 들어간다(`relevance-judge-auto.mjs examplesFor`). 2차에는 넣지 않는다 — 두 판정자가 같은 예시를 보면 독립성이 준다.
- `relevance-eval-report.mjs` 는 사람 `모름`을 일치율 계산에서 뺀다(이번에 한 줄 고쳤다). 모름을 오답으로 세지 않는다.
- 5번 지시(사람 채점 트랙) 세션이 웹 화면을 만든다면 같은 테이블·같은 세 값을 쓰면 된다.
  - 모집단 규칙: 신규 = 자동 승인 아님, 감사 = 자동 승인 ∧ 사람 채점 없음.
  - 순수 함수 `pickGradingSample` 을 그대로 재사용한다.

## 3. 킬스위치 — 수치와 이유

- **창**: 가장 최근 사람 채점 50건. 사람 채점이 relevant·irrelevant 인 것만 센다(모름 제외).
- **오류**: 자동 승인했는데 사람이 irrelevant 라고 한 것.
- **문턱**: 오류 ≥ `ceil(n·p0 + 2·√(n·p0·(1−p0)))`, `p0 = 7%`.
  - n=50 → **8건**(정확도 84% 이하)
  - n=25 → 5건
  - n=10 → 3건
  - 10건 미만이면 판정하지 않는다(워밍업).
- **p0 = 7% 인 이유**
  - 오늘 잰 기준선은 소비재 1차·2차 일치율 93.3%(537건)다. 불일치 6.7% 가 판정자 한 명의 오류율 상한 근사치다.
  - 둘이 동의한 행의 오류는 이보다 낮아야 정상이다. 그러니 7% 를 넘는 오류가 **유의하게** 보이면 무언가 바뀐 것이다(모델·기준·소스).
- **이 문턱의 오탐·탐지율** (이항분포 정확 계산, 창 50 · 문턱 8)
  - 참 오류 5% → 끌 확률 0.3%
  - 참 오류 7% → 2.2% (오탐)
  - 참 오류 10%(통과선 90%) → 12%
  - 참 오류 15% → 48%
  - 참 오류 20% → **81%**
  - 참 오류 30% → 99%
  - 즉, 통과선 근처의 정상 흔들림에서는 거의 안 꺼지고, 정확도가 80% 아래로 내려가면 창 하나 안에서 대부분 잡는다.
- **"N일 연속 X% 미만" 대신 창을 쓴 이유**
  - 하루 5건이면 일별 정확도가 1건마다 20%p씩 흔들린다. 연속 조건을 걸면 오탐을 피하려고 문턱을 크게 낮춰야 한다.
  - 50건 창은 곧 "최근 약 10평일"이다. 연속 기간을 표본 수로 바꿔 적은 것이다.
- **확인 불가도 끈다**
  - 시행 14일(워밍업)이 지났는데 최근 14일 감사가 20건 미만이면 끈다. 20건은 기대치 50건의 40% 다.
  - 감사가 안 돈다는 것은 조건 3이 무너졌다는 뜻이다. 오류 0으로 접지 않는다(§7.1).
- 감사 창 조회가 실패해도 끈다.
- **꺼질 때 하는 일**
  - 승인 0건
  - `agent_runs` step `blocked`(사유 포함)
  - GitHub `::warning::`
  - Notion 일일 상태 로그 CTO 행 `사람판단필요=true`
    - `recordStatusLog`. 워크플로에 기존 `NOTION_API_TOKEN` 시크릿을 같은 목적으로 넣었다(§10.2 "넓히는 것 아님").
  - 이미 찍힌 `auto_approved_at` 은 지우지 않는다(사실이었으니까). 사람 채점이 있으면 어차피 human_verdict 가 이긴다.
- **다시 켜는 법**
  - 기계는 켜지 않는다. 꺼진 동안엔 새 승인이 없어 감사 모집단도 늘지 않는다.
  - 사람이 기존 자동 승인 행을 더 채점해 창이 문턱 아래로 돌아오면 다음 실행에서 열린다.
  - 원인을 모르겠으면 리포 변수 `AUTO_APPROVAL_ENABLED=false` 로 완전히 내린다.

## 6. 단계적 확대 규칙 — 설계만, 구현하지 않음

- 각 단계는 **새 rule 태그**로 기록한다(`rr-v1` → `rr-v2` …). 킬스위치 창도 **태그별로** 따로 센다. 새 조건의 오류가 옛 조건의 좋은 성적 뒤에 숨지 않게 하기 위해서다.
- 올리는 조건은 모두 "현재 단계 창이 4주 연속 문턱 아래"이고, 올린 뒤 2주는 다시 워밍업이다.

- **1단계 (지금)** `rr-v1`
  - 조건: 1차 relevant ∧ 2차 relevant
- **2단계** `rr-v2` — 영향 큰 것부터 넓힌다
  - 조건: 1차 relevant ∧ 2차 unknown ∧ 1차 `impact='high'`
  - 이유: 2차가 "판단 불가"라 한 것 중 1차가 영향이 크다고 본 행은 놓치는 비용이 크다. 오편입 비용(프롬프트 잡음)은 작다.
  - 올리는 조건: rr-v1 감사 창 4주 연속 정확도 ≥ 93%(= 50건 중 오류 ≤ 3)
  - 감사 표본은 태그별 최소 3건/일이다.
- **3단계** `ru-v1`
  - 조건: 1차 relevant ∧ 2차 unknown(영향 무관)
  - 올리는 조건: rr-v2 창 4주 연속 ≥ 90%
- **넣지 않는 것 — 영구 사람 몫**
  - 1차·2차가 **반대**인 행(R·I / I·R). 불일치는 확실히 사람이 봐야 할 것이다(09-27 설계 §3-1).
  - **폐기 방향**(I·I 자동 폐기). 되돌릴 수 없어서(30일 purge) 문턱이 따로 필요하다: II 100건 무오류(09-27 설계 §4-3 A 레인). 이 문서 범위 밖이다.
- **내리는 규칙**: 어느 단계든 킬스위치가 걸리면 그 태그만 끄고 한 단계 아래로 돌아간다. 2회 연속이면 `rr-v1` 까지 내리고 사람 판단으로 올린다.
