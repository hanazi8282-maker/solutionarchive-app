### 2-15. 10차 — L-60 + L-64 를 한 축으로 합쳐 설계 (2026-09-07, append-only)

남헌 지시: *"1. 같이 설계 진행해줘 … 두가지 모두 진행후 완료."* — L-60(원 관측 판별 키)과
L-64(근거가 어느 주장을 받치는지 안 봄)를 **같은 뿌리**로 보고 한 라운드에 설계했다.

**(0) 한 문장 진단**

산식이 세는 단위는 "행"인데, 세야 하는 것은 **"서로 다른 관측 × 그 관측이 실제로 받치는 주장"**이다.
L-60 은 앞쪽(관측)이 접힌 것이고, L-64 는 뒤쪽(주장)이 접힌 것이다.

**(1) 스키마 — 마이그 `20260907000001_case_evidence_observation_keys.sql` (⚠️ 미적용)**

- `observation_key text` — 이 행이 전하는 원 관측의 이름. 같은 관측을 옮긴 행끼리 같은 값.
  CHECK `^[a-z0-9]+(-[a-z0-9]+)*$` (빈 문자열 거절), 인덱스 1개.
- `supports_metric boolean` — 이 행이 무브의 수치를 직접 받치는가. 서사만 받치면 false.
  CHECK: `case_move_id IS NULL` 인 케이스 단위 근거에는 `true` 를 못 쓴다(받칠 수치가 없다).
- **둘 다 nullable.** NULL 은 "아니다"가 아니라 **"확인하지 않았다"**다. 파일 (3)에 검증 쿼리
  양성 2 · 음성 3, (4)에 키 규약과 9차까지 원문 확인한 행만 담은 백필 UPDATE 를 주석으로 적어 뒀다.
- §12-5 대로 **적용은 남헌이 대시보드 SQL Editor 에서.** 이 라운드에서 적용하지 않았다.

**(2) 산식 — `lib/cases/draft.ts`**

- `foldObservations(evidence)` 신설 → `{ keys: Set, unkeyed: number }`.
- 경로를 둘로 나눴다. **문서 성격 경로**(법정 공시 `attested`, 비자기보고 1차 `nonSelfPrimary`)는
  키를 요구하지 않고 `supports_metric === false` 로 **명시된** 행만 뺀다 — 그쪽 A 는 개수가 아니라
  문서의 법적 책임에서 나오기 때문이다. **개수 세는 경로**(교차 확인)는 `supports_metric === true` +
  키 있는 행만 세고, **키 가짓수 ≥ 2** 여야 A 다.
- 자기보고 1차 + **다른 키** ≥ 1 → B. 같은 키뿐이면 C. 이게 L-60 의 실제 수정이다.
- 세지 않은 행은 사유에 남긴다: `(교차 확인 후보 3건 중 3건은 관측 키·수치 뒷받침 미기재라 세지 않았다)`.
- `GradeResult.provisional` 신설 — "키가 없어 판정 못 함"으로 내려간 등급에 표시가 붙는다.

**(3) 백필 전 투영 (`regrade --dry --force`, 32 무브) — 판정이 아니라 투영이다**

```
이전 A13 · B5 · C13 · D1
이후 A12 · B0 · C19 · D1     (바뀐 것 6개 / 잠정 15개)
```

- **B 5건이 전부 C 로 내려간다.** 남헌이 3순위에서 지적한 그대로다 — *"그 '다른 도메인 1건'이 같은
  공시를 옮겨 적은 것이면 B 도 사실은 C 입니다."* 다만 지금 내려가는 이유는 "옮겨 적은 게 확인됐다"가
  아니라 **"아직 안 적었다"**이다. 백필하면 일부는 B 로 돌아온다(다른 관측이 실제로 있는 경우).
- A 는 12개가 그대로 남는다. 법정 공시·비자기보고 1차로 선 A 라 키와 무관하기 때문이다.

### 3-7. 사고 11 — §7.1 재발, 이번엔 내 쿼리가 틀렸다 (2026-09-06 추가, append-only)

| # | 사고 | 정체 | 발견 경로 |

**정체.** 마이그 `20260906000002` 는 컬럼을 추가하지 않는다. `posts_status_check` 의 **허용 값**에
`pending_review` 를 더할 뿐이다. 그런데 확인 스크립트가 `from('posts').select('pending_review')` —
**값을 컬럼명 자리에** 넣고 조회했다. 그런 컬럼은 적용 전에도 후에도 없으므로 42703 은 필연이다.
검사가 판별력이 0 이었다. 그런데 그 0 을 "미적용"이라는 **판정**으로 읽었다.

사고 6("찾지 못함"을 "없음"으로 접음)과 같은 모양이고, §7.1 이 정확히 막으라는 것이다.

**왜 안 걸렸나.** 42703 은 "없다"고 말하는 것처럼 생겼다. `column ... does not exist` 라고 적혀 있으니

**도출된 규약(§7.1 에 덧붙임).**

- **에러 메시지가 말하는 "없음"의 주어가 무엇인지 확인하라.** 42703 의 주어는 컬럼명이다.
  마이그레이션의 적용 여부가 아니다.
- **검사가 어떤 경우에 다른 답을 내는지 먼저 답해 보라.** "적용됐으면 뭐가 달라지나?"에 답할 수 없는
  검사는 검사가 아니다. 이 조회는 두 경우 모두 42703 이었다.
- **CHECK 어휘는 읽어서 알 수 없다 — 넣어 봐야 안다.** 스키마 조회로 판정하려 들지 말고 INSERT 프로브를
  쓰고, 프로브를 못 돌리는 상황에서는 양성도 음성도 아닌 **확인 불가**로 남겨라.
  (`case-pipeline-verify.mjs` 에 그렇게 박아 뒀다. `--probe` 없이는 판정하지 않는다.)
- **일회용 스크립트로 낸 판정을 로그에 적지 마라.** 지워 버리면 어떻게 확인했는지 아무도 못 본다.
  이번에도 `.tmp-state.mjs` 를 지운 뒤라 "어느 쿼리에서 42703 이 났나"를 되짚는 데 시간이 들었다.
  판정으로 쓸 확인은 **커밋되는 검사기 안에** 넣는다.
